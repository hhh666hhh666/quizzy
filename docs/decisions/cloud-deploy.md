# 决策日志：quizzy 怎么搬到云服务器上

## 2026-10-01 21:03 · grill（5 轮）

起因是「我想把项目部署到云服务器，从此不在本机上运行」这一句话。

开问前先摸清了两件事，它们直接改变了下游设计：

- **数据几乎为零。** 对本地 `quizzy-mysql` 做只读查询：`user` 1 行、`question` 34 行（**`owner_id` 全为 NULL，34 道全是 Flyway `V2__seed_questions.sql` 的种子题**）、`paper` 0 行、`quiz_session` 2 行、`quiz_answer` 4 行、`question_stat` 2 行，整库 **0.4 MB**。也就是说「本机独有」的只有 1 个账号和 4 条作答，迁移方案不需要讨论停机窗口。
- **`nginx.conf` 只转发 `/api/` 与静态资源。** 所以 `/v3/api-docs` 与 `/swagger-ui.html` 走的是 SPA 回退，**从来没有对外暴露过**——只有直连宿主机 8080 才看得到。这条后来省掉了一个本来以为必须做的改动（见 D4 的后果）。

这次 grill 会推翻两条已写进仓库的决策：[ADR 0013](../adr/0013-github-actions-gate-no-auto-deploy.md)（CI 只做门禁、不做部署）与 [`docker-run-setup.md`](./docker-run-setup.md) 的 **D3**（纯本机 localhost 自用）。D3 当时已经预警过：「哪天要放到能被别人访问的环境，密钥和端口映射必须重来一遍」——这里是那笔账的到期日。

### D1 · 访问范围：公开注册，谁都能用

- **决策**：对公网开放，任何人注册即可使用。
- **因为**：用户直接选定。这也是「搬到常驻机器上」的真正动机——不是自己用得更爽，而是要让别人也能用。
- **后果**：产品定位从「个人自学的刷题工具」变成「对公网开放的注册制服务」，`docs/requirements/scope.md` 的定位段与「明确不做」都要改，并新增合规义务。**单独记一条 ADR**（[0017](../adr/0017-public-signup-service.md)），因为它改变的是产品边界，不是部署形态。
- **来源**：Q1-1

> **Q1-1 · 云服务器上的 quizzy，将来谁会访问它？**：A. 只有我自己／B. 我和少数几个朋友／C. 公开，谁都能注册
>
> ➡️ 推荐：A。吻合 `docs/requirements/scope.md` 写的「个人自学刷题工具」定位，安全面最小、不必备案。
>
> **你的回答**：C（公开，谁都能注册）

### D2 · 云目标：用现有的阿里云 ECS

- **决策**：不新购，用已有一台阿里云 ECS。规格 **2C2G / 包年包月**，系统 **Alibaba Cloud Linux 4**，架构 **x86_64**，地域中国大陆。
- **因为**：用户直接选定。
- **后果**：
  - **2C2G 是这次所有技术选择里最硬的一条约束。** 它直接把 D4 的「服务器上构建」判死（Maven 构建必 OOM），也让 JVM 堆与 MySQL 缓冲池必须显式钉死、并额外建 swap 兜底。
  - **大陆 + 域名 ⇒ 必须 ICP 备案**，且备案要求 ECS 包年包月剩余 ≥ 3 个月（用户的实例满足）。
  - **x86_64** 让 CI 无需 `--platform linux/arm64` 构建矩阵。
  - **Alibaba Cloud Linux 4 原生用 `moby` 包提供容器引擎**（命令、服务名 `dockerd`、API、镜像都与标准 Docker 兼容），不必去装 docker-ce 那一套。
- **来源**：Q1-2、Q2-2、Q2-3、Q4-1

> **Q1-2 · 服务器从哪来？**：A. 已有一台云服务器／B. 还没买，准备新购／C. 有别的机器可用
>
> ➡️ 推荐：B（若新购则建议 2C4G / 40G+ SSD / Ubuntu 24.04 LTS）。
>
> **你的回答**：A（已有一台云服务器）
>
> **Q2-2 · 这台云服务器在哪个地区？** ➡️ 推荐：大陆（若要给国内朋友用则只能选它，代价是备案）。**你的回答**：中国大陆
>
> **Q2-3 · 服务器装的是什么系统？** ➡️ 推荐：Ubuntu 22.04 / 24.04 LTS（apt 系最省心）。**你的回答**：Alibaba Cloud Linux 4
>
> **Q3-2 · 这台 ECS 是 x86_64 还是 ARM64？（决定 CI 用什么 `--platform`）** ➡️ 无法推荐，取决于实例。**你的回答**：x86_64
>
> **Q4-1 · ECS 的规格与计费方式？** ➡️ 推荐：2C4G / 包年包月（包年包月是备案的硬条件）。**你的回答**：2C2G，包年包月

### D3 · 本机保留 dev，只把 prod 搬走

- **决策**：本机只写代码；`docker-compose.dev.yml` 与本地 MySQL 容器**原样保留**，prod 整套搬到云上。
- **因为**：采纳推荐。日常改代码要的是快速迭代，连云端数据库调试既慢又把生产库当试验田。
- **放弃**：B「本机不再跑任何容器」（连 Docker Desktop 都卸掉）——本地就没数据库了，开发体验崩掉；C「本机留一份完整副本做灾备」——两份数据要同步，且要防「本机副本悄悄变成唯一真相源」。
- **后果**：`docker-compose.prod.yml` 的语义从「本机 prod 编排」变成「云上编排」；`scripts/deploy.sh` 的定位要跟着变。本机 `.env` 与云上 `.env` 从此是两份不同内容，`.env.example` 只有一份就不够了。
- **来源**：Q1-3
- 相关：[ADR 0007](../adr/0007-dev-prod-compose-with-bind-mount.md)、[ADR 0016](../adr/0016-cloud-deploy-with-release-pipeline.md)

> **Q1-3 · 「从此不在本机上运行」——本机还要不要留开发环境？**：A. 只写代码，保留 dev／B. 本机不再跑任何容器／C. 留一份完整副本做灾备
>
> ➡️ 推荐：A。改动最小、迭代最快；保留 `docker-compose.dev.yml`。
>
> **你的回答**：A

### D4 · 镜像在 CI 构建，推 ACR，tag 自动部署

- **决策**：推 tag 触发 GitHub Actions，构建两个镜像推往**阿里云 ACR 个人版**，再 SSH 到 ECS 拉取并重启。
- **因为**：用户在看过三个方案的机制与代价对比后选定。它的两个决定性优势：① 云机不吃构建内存（2C2G 下这是唯一可行解）；② **不推翻 ADR 0013 关于「人何时上线」的那半**——0013 反对的是「CI 直接改线上」，但用户明确选择连这半也一起改（见 D6），因此 0013 整体被 [ADR 0016](../adr/0016-cloud-deploy-with-release-pipeline.md) 取代。
- **放弃**：
  - 「服务器上构建，手动部署」——`compose up --build` 在 2C2G 上必 OOM。**注意这条在本机是更优解**：两个 Dockerfile 的默认依赖源（阿里云 Maven 镜像 / npmmirror）在大陆服务器上正好是对的，是 2C2G 而非网络否决了它。
  - 「本机构建后 `save`/`scp`/`load`」——不需要 registry 账号且构建最快，但本机仍在部署路径上，与初衷相反。
- **顺带发现（修正了一条原本以为必须做的改动）**：删掉 `ports: 8080:8080` 之后 Swagger 自然就不对外了——因为 `nginx.conf` 本来就只转发 `/api/` 与静态资源，`/v3/api-docs`、`/swagger-ui.html` 落进 SPA 回退。所以**不需要关闭 springdoc**，也就不会发生「关 Swagger 连带打断 healthcheck」的连锁，[ADR 0012](../adr/0012-healthcheck-probes-api-docs.md) 的探测端点保持不变。
- **来源**：Q1-4、Q2-1
- 相关：[ADR 0016](../adr/0016-cloud-deploy-with-release-pipeline.md)

> **Q1-4 · 镜像在哪构建、怎么送到服务器、上线由谁触发？**：A. 服务器上构建（复用现有 `deploy.sh`）／B. CI 构建推 registry，手动 pull／C. CI 构建推 registry + tag 自动部署／（补充）D. 本机构建后 `scp` 过去
>
> ➡️ 推荐：B。云机不吃构建内存，且保住 ADR 0013 的本意。
>
> **你的回答**：要求把选项解释一遍，之后选 **C**（推 tag 即上线，全自动）

### D5 · 镜像仓库：阿里云 ACR 个人版

- **决策**：推 ACR 个人版，命名空间 `quizzy`。
- **因为**：采纳推荐。CI 跑在境外 GitHub runner、服务器在大陆，两端的最优选择是相反的；ACR 让服务器这一端（拉取，更频繁、更贴近故障）变快变稳，代价只是 CI 那一端跨境推送。
- **放弃**：GHCR（CI 侧零配置、推送原生快，但大陆 ECS 拉取常慢且不稳）；两个都推（最稳，但两套凭据 + 两套 tag 对齐）。
- **坑（已查实）**：**ACR 个人版不支持 AccessKey 推送**，必须用「阿里云账号全名 + ACR 固定密码」（在「访问凭证」里单独设），否则 CI 会一直 401。
- **来源**：Q3-3
- 相关：[ADR 0016](../adr/0016-cloud-deploy-with-release-pipeline.md)

> **Q3-3 · 镜像推到哪里？（CI 在境外、服务器在大陆，两端最优相反）**：A. 阿里云 ACR 个人版／B. GHCR／C. 两个都推
>
> ➡️ 推荐：A。
>
> **你的回答**：A

### D6 · 接受 Flyway 无人值守自动迁移，加三道保险

- **决策**：接受自动迁移，配三道保险——① 部署脚本在 `up -d` 前强制备份；② CI 新增 `flyway-verify` job，在临时 `mysql:8` 上完整跑一遍 `db/migration`；③ 纪律：迁移只做向后兼容的加表 / 加可空列，破坏性变更不走自动部署。
- **因为**：用户在三个选项里选了带保险的自动迁移。**这一条是 ADR 0013 被取代的关键**——0013 的原话是「项目里有 Flyway 迁移和题库数据，不该被一条无人值守的流水线自动改动」，既然要自动部署，就必须正面回答它而不是绕过去。
- **放弃**：B「迁移必须人工把关」（CI 发现新增 `V*.sql` 就停在上线前等人确认——最保守，但等于把「自动部署」撕开一个口子）；C「退回手动 pull」（保住 0013 结论不变）。
- **⚠️ 已知弱点**：第三道保险是靠人守的。它一破，前两道只能证明「语法能跑」，不能证明「数据安全」。第二条保险是纯赚的——**在此之前 `mvn test` 完全不碰数据库，迁移从未被任何流程验证过**。
- **来源**：Q3-4
- 相关：[ADR 0016](../adr/0016-cloud-deploy-with-release-pipeline.md)

> **Q3-4 · tag 自动部署意味着 Flyway 迁移会在无人值守时自动跑。这一条怎么定？**：A. 接受自动迁移 + 三道保险／B. 迁移必须人工把关／C. 那就不自动部署了
>
> ➡️ 推荐：A。
>
> **你的回答**：A

### D7 · HTTPS：acme.sh + DNS-01

- **决策**：用 `acme.sh` 配合阿里云 DNS 插件做 **DNS-01** 验证签发 Let's Encrypt 证书，自动续期。
- **因为**：采纳推荐，且理由是**它把「证书」和「备案」解耦**。备案要 1–3 周，那期间域名解析不能指向大陆 ECS；HTTP-01 在这两周里什么都干不了，等于把「备案通过 → 签证书 → 配 HTTPS → 首次上线」全压到同一天。DNS-01 只查 DNS TXT，**不在乎域名解析到哪、也不碰 web 端口**，所以证书可以在备案提交后第二天就装好，备案一通过改个解析就完事。
- **放弃**：
  - **certbot + HTTP-01**：不是它不好，是它的验证方式与备案互斥——它是唯一一个「备案前完全不可用」的方案。附带成本：在 Alibaba Cloud Linux 4 上要带 Python 依赖，而 `acme.sh` 是单文件 shell。
  - **阿里云免费 SSL 证书**：它是唯一一个**会因为你忘记而整站挂掉**的方案。已查实阿里云的证书托管服务**只对付费正式证书开放，免费版不支持自动托管**，所以「每 90 天手动重来一遍」是产品限制而非使用习惯。对一个公开注册的站点，证书失效 = 所有访客看到红色警告页，而现在没有任何监控能提前提醒。
- **⚠️ 它的代价（不是零成本）**：DNS-01 需要在服务器上保存一个阿里云 DNS 的 AccessKey。缓解：建**仅 DNS 解析权限**的 RAM 子账号、`~/.acme.sh/account.conf` `chmod 600`、定期轮换。用户在被问到「若不能接受服务器上放 DNS 密钥就改用 certbot + HTTP-01」时，未提出反对。
- **来源**：Q4-3、Q5-1
- 相关：[ADR 0016](../adr/0016-cloud-deploy-with-release-pipeline.md)

> **Q4-3 / Q5-1 · HTTPS 怎么上？**：A. Let's Encrypt + certbot 自动续期／B. 阿里云免费 SSL 证书／C. 先 HTTP，HTTPS 以后再说
>
> ➡️ 推荐：A，但走 DNS-01（`acme.sh` + 阿里云 DNS 插件）而非 HTTP-01。
>
> **你的回答**：先要求写出推荐原因与不选另两个的理由，之后接受该方案

### D8 · 备份存阿里云 OSS

- **决策**：每日 `mysqldump` 上传 OSS，配生命周期规则自动过期，本地保留 7 天。调度用 **systemd timer**。
- **因为**：采纳推荐。同地域内网免流量费、0.4 MB 的库成本几乎为零，且是**异地**——磁盘挂了备份还在。
- **放弃**：B「服务器本地另一块盘」（省钱但同机，等于把现在的「备份与数据同在 E 盘」问题在云上重演）；C「拉回本机」（异地且免费，但本机重新回到链路里）。
- **顺带**：`docs/operations/backup.md` 明确写着恢复流程「**尚未演练**」，这次一并补上。

### D10 · 注册准入门槛：图形验证码 + IP 限流 + 封禁开关；邮箱验证推迟为独立变更

- **决策**：公开注册的准入门槛定为「图形验证码 + 注册接口按 IP 限流 + 一个最小的账号封禁开关」，并且**额外加邮箱验证**；但邮箱验证**推迟到部署链路跑通之后单独做**（单独 PR + 单独 ADR + 一次 Flyway 迁移）。
- **因为**：用户在门槛三档里选了比推荐更高的「中等包（再加邮箱验证）」，又在「什么时候做」里选了先做部署——这个组合是对的：部署这条链路（备案、ACR、CI 自动部署、证书、备份、2C2G 调优）本身全是第一次，混着功能开发会让「到底哪一层坏了」难以判断。
- **放弃**：A「不设门槛，保持现状」（公开站点会在几天内被脚本注册灌满，且没有任何清理手段）；C「邮箱只记录不强制（软验证）」（门槛实际并不存在，SPF/DKIM 的活一样要做）。
- **已记录的后续偏好**（做那一步时的输入，不是本次的决策）：邮箱作为**登录名**、用户名降为昵称、SMTP 用**现有个人邮箱**。
  ⚠️ **这三条放在一起有冲突**：邮箱即登录名意味着「收不到验证信 = 登不进来」，而个人邮箱 SMTP 恰恰是最容易进垃圾箱、且有发信限额的通道。做那一步时要重新评估发信通道。见 [待办](../todo/2026-10-01-TODO-邮箱验证.md)。
- **注**：「封禁开关」与 `docs/requirements/scope.md`「明确不做 RBAC」不冲突——它是一个布尔字段级的开关，不是权限体系，但需要作为例外写进 scope。
- **来源**：Q4-2、Q5-2、Q5-3、Q5-4

### 本次明确拒绝收录进 `CONTEXT.md`

`CONTEXT.md` 是**纯领域术语表**（题目 / 会话 / 错题本那一类），不含通用工程概念与外部事实。本次定下的这些词一个都不该进去：

| 词 | 为什么不收 |
|---|---|
| 备案 / ICP | 外部合规流程，是阿里云的办事环节，不是这个上下文里的概念 |
| 镜像仓库 / registry / ACR | 通用 DevOps 概念 |
