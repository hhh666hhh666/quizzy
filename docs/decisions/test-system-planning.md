# 决策日志：给 quizzy 建一套测试系统

## 2026-10-03 23:00 - 2026-10-04 10:00 · 第 4 次 grill

起因是「为本项目构建一个全自动测试系统」。前四十分钟在 Ask 模式把**边界**逐个探清（全自动到什么程度、UI 测试包含不包含、排版能不能保证、能不能让 agent 模拟用户），随后切 Agent 模式用 grill 把设计树走完。

开问前先读准的事实：

- 后端 8 个 Controller，按模块分包（auth / category / question / paper / quiz / wrongbook，其中 category 下有两个）；而**测试类只有 2 个**、共 7 个 `@Test`，全是纯 JUnit。
- `ci.yml` 六个 job，**从头到尾没有任何一次把后端真正跑起来**——`mvn test` 不拉 Spring、镜像 job 只 `docker build`，文件末尾还明写「刻意不 `docker compose up`」（原因是仓库没有 `.env`，而 `${QUIZZY_JWT_SECRET:?...}` 是必填断言）。
- `release.yml` 已有**半套一次性环境**：`flyway-verify` job 在一次性 `mysql:8` 上按序重放迁移。但它只验「迁移语法能跑」，不起后端。
- 两个前端工程都**没有测试依赖**，这是 `docs/testing.md` 明写的刻意选择（「保持零额外依赖、随手能跑的个人形态，而不是遗漏」）。
- 迁移只有 `V1__init.sql` / `V2__seed_questions.sql`。
- `docs/testing.md` 被 **10 处**引用、跨 8 个文件。

其中三条事实直接决定了后面的形状：**「后端从未被真跑起来」**是要补的最大断点；**「已有半套一次性环境」**意味着端到端的环境不必从零发明；**「前端零依赖是刻意选择」**意味着任何前端测试工具都得解释自己为什么该破例。

### D1 · 不做视觉回归，UI 排版零自动化

> ⚠️ **本条已被下面的 D14 收紧**：「排版正确性完全交给人眼」不成立——排版里可机械判定的几何事实改由端到端层的断言覆盖。**视觉回归仍不做**，下面三条理由不变。保留原文是为了留下当时的推理。

- **决策**：**明确不做**截图逐像素比对；排版正确性完全交给人眼。
- **因为**：三条——① 排版差异对业务正确性无影响，且**开发时打开页面当场可见**，不像判分反馈那类静默错误；② 单人开发**没有第二双眼睛**去审「新基线对不对」，等于自己给自己签字；③ 基线是入库的二进制会持续膨胀，而 CI runner 无中文字体，中文界面截图会渲染成豆腐块，基线永远对不齐。
- **放弃**：做视觉回归（成本不在搭建，而在于它把「合法的 UI 改动」永久变成「人工核对基线 + 更新基线」的流程负担）。
- **来源**：追问「第 4 档维护成本是什么」「能确保 ui 排版正确吗」
- 相关：[ADR 0020](../adr/0020-layered-test-system.md)

### D2 · codegen 只当起草工具，不当架构

- **决策**：可用 Playwright codegen 录制来**探路与起草**，但产物必须人工重写（换稳定定位器、去死等、补业务断言）；**录出来的代码不进库**。
- **因为**：录制忠实记录了人的全部行为——脆弱的文案定位器（页面上「提交」「确定」有重名）、把人的停顿录成 `waitForTimeout` 死等、无关的鼠标动作；且它录的是**某一次点击路径**，不是**规则**（多选全对才得分这类规则，录一遍是证不出来的）。
- **放弃**：把「录制 + 封装 Skill」当成整个测试系统的核心——它解决「怎么写」，不解决「写什么、测到哪一档、放进哪条流水线」。
- **来源**：用户提出的「Playwright Codegen + Skill」方案
- 相关：无（属实践约定，写进 [《测试系统说明》](../testing/系统说明.md)）

### D3 · 三层都做：单元保留，新增接口与服务集成、端到端

- **决策**：L1（单元，保留现状约束）+ L2（接口与服务集成）+ L3（端到端），三层一起建。
- **因为**：三层互补，各自有独有的问题——接口层抓契约、鉴权与**数据边界**（「拿别人的 id 改写数据」只有它能问），端到端抓「后端返回了但前端没渲染」（2026-10-03 那个判分反馈 bug 正是这一类），两者都不该承担纯逻辑枚举。
- **放弃**：只做端到端（放弃契约与越权覆盖）；只做接口层（放弃界面行为与前后端契约断裂）。
- **来源**：Q1（选 b）
- 相关：[ADR 0020](../adr/0020-layered-test-system.md)

### D4 · L2 进 `quizzy-server`、L3 新建顶层 `e2e/`

- **决策**：接口与服务集成测试放 `quizzy-server/src/test`（**挂独立 Maven profile**）；端到端测试新建**顶层目录 `e2e/`**，带独立 `package.json`。
- **因为**：两者是不同技术栈（Java / Node）与不同作用域（单端 / 跨端），硬凑一起会两不像。⚠️ 关键约束：L2 必须走独立 profile，`mvn test` 保持**不需要起任何服务**——否则会破坏 `docs/testing` 明写的既有约束。
- **放弃**：全部塞进 `quizzy-server/src/test`（端到端是跨端的，塞不进 Maven）；端到端塞进 `quizzy-web`（会让 PC 工程被迫背起跨端职责）。
- **来源**：Q2（选 c）
- 相关：[ADR 0020](../adr/0020-layered-test-system.md)

### D5 · 五个测试术语定名，但**不进** `CONTEXT.md`

- **决策**：把「单元测试 / 接口测试 / 服务集成测试 / 端到端测试 / 探索测试」五个词的定义钉在 [《测试系统说明》](../testing/系统说明.md)，并明确 `接口测试 ≠ 集成测试`（前者只是后者的一种形态）。**`CONTEXT.md` 不动**。
- **因为**：术语表只收「本上下文独有的概念」（`CONTEXT.md` 的门槛，「知识点」被取消就是这个道理）；这五个是**通用技术词**，收进去等于污染术语表。但**定名本身仍要做**——本次花了好几轮才把「L2 是不是就是调接口」问清，根因就是「集成测试」被当成万能词。
- **放弃**：把测试词收进 `CONTEXT.md`；或不定名、继续用含糊的「集成测试」笼统称呼。
- **来源**：Q3
- 相关：与 [移动端那轮 D10](./mobile-and-miniprogram.md)「三条叫法都不进术语表」同类判断

### D6 · `docs/testing/` 目录，`testing.md` 移为 `README.md`

- **决策**：新建 `docs/testing/` 目录；原 `docs/testing.md` 用 `git mv` 移成 `docs/testing/README.md`，并改全仓引用。
- **因为**：测试要从一份文档长成一个主题目录（现状 / 设计 / 探索任务书）；**同名共存**（`testing.md` 与 `testing/`）虽合法，但 `check-doc-links.sh` **不会报错**，意味着这种混淆不会被任何自动检查拦住，迟早出乱子。
- **代价**：`docs/testing.md` 被 10 处引用、跨 8 个文件，一次性全改。选它而不选「换个目录名」，是因为换名仍在撞 `testing` 这个前缀，且改动面一样大。
- **放弃**：照原样同名共存；把目录改名规避。
- **来源**：Q4（选 c）
- 相关：[ADR 0006](../adr/0006-bare-array-import-contract.md)（引用漂移是这里最贵的失效）

### D7 · 走短命分支 + PR，不直推 master

- **决策**：本次改动走短命分支 → PR → squash 合并。
- **因为**：本次横跨 CI、文档、代码三块，PR 能在合并前看整体 diff；且符合 `docs/development/contributing.md` 的约定。
- ⚠️ 附带提醒：动手前先确认 `docs/worklog/` 下那个别的会话遗留的未提交改动**不属于本次**，别重复 2026-10-03 那次 `git add -A` 误扫。
- **来源**：Q5（选 b）

### D8 · `README` 管现状、`系统说明` 管设计

- **决策**：`docs/testing/README.md` 只放**现状与索引**（有哪些测试、怎么跑、盲区、新测试放哪）；`docs/testing/系统说明.md` 只放**设计意图**（为什么分三层、各层边界、能保证/不保证什么、加功能时怎么同步）。事实只在 README 出现一次，理由只在系统说明出现一次。
- **因为**：两份都写就会漂——这是 [ADR 0006](../adr/0006-bare-array-import-contract.md) 的教训。合并成一份则会让一份文档既当索引又讲设计、越写越厚。
- **放弃**：合并成一份；或让系统说明当唯一权威、README 只留一行指针（丢掉「安全网现状」这个高频入口）。
- **来源**：Q6（选 a）

### D9 · 测试库用 Testcontainers

- **决策**：接口与集成测试用 **Testcontainers** 声明式起 MySQL 8。
- **因为**：只有它让「本机也能跑」与「CI 也能跑」统一——改代码时能自查，符合项目「随手能跑」的形态。
- **放弃**：① CI service 容器（照 `release.yml` 写法）——本机跑不了，测试会变成「只有 CI 能验」的黑盒；② H2 内存库——方言差异大、迁移脚本未必跑得通，等于把「测试环境与真实环境不一致」请回来（[ADR 0006](../adr/0006-bare-array-import-contract.md) 的同类教训）。
- ⚠️ 附带约束：`mysql:8` 镜像本机已有，但本机 Docker Hub 不可达（[ADR 0010](../adr/0010-china-mirrors-for-build-deps.md)），首次拉取要走镜像站。
- **来源**：Q7（选 a）
- 相关：[ADR 0020](../adr/0020-layered-test-system.md)

### D10 · `release.yml` 不加测试门禁

- **决策**：接口层与端到端只在 `ci.yml` 跑，发布流水线保持现状（版本门禁 → 迁移重放 → 构建推 ACR → 部署）。
- **因为**：CI 已在 master 上跑同一套，而 tag 必然建立在已绿的提交上，再跑一遍是重复烧 runner 并拖慢发版；真出现「CI 绿、线上坏」那是**环境差异**，在 CI 上跑也拦不住，归 `docs/operations/runbook.md`。
- **放弃**：`release.yml` 加 `needs: [e2e]`。
- **来源**：Q8（选 a）
- 相关：[ADR 0016](../adr/0016-cloud-deploy-with-release-pipeline.md)

### D11 · `data-testid` 按需加

- **决策**：只给「同一页会重复出现或文案会变」的元素加 `data-testid`（答题页选项、判定结果区、解析区），其余用语义定位（role / label）。
- **因为**：全量加等于给每个元素挂一个纯测试负担并污染源码；一个不加则重蹈「文案重名导致定位错元素」的坑。
- **放弃**：全量加；完全不加。
- **来源**：Q9（选 c）

### D12 · 端到端覆盖清单固定，移动端本轮不纳入

- **决策**：覆盖范围锁定一条主链路——注册 → 登录 → 建题（含多选）→ 组卷 → 答题（判对 / 判错 / 多选全对才得分）→ 结算 → 错题本 → 断点续答。**清单之外一律不测**。移动 H5 **本轮不纳入**。
- **因为**：移动端主线 2026-10-03 才走通、小程序编译目标与 `/m/` 部署未做，此时把端到端压上去会被两处改动同时拉扯；且移动端组件库（wot-design-uni）与 PC（Element Plus）渲染出的 DOM 差异大，复用率没有想象中高。
- **放弃**：本轮就用同一套 spec 加一个移动视口 project。
- **来源**：Q10（选 b）
- 相关：`docs/todo/2026-10-03-TODO-移动端与小程序落地.md`

### D13 · 新增功能时用「映射表 + 同 PR + 机械守卫」同步测试

- **决策**：三件套——① 一张「改动 → 补哪层」映射表（在 [《测试系统说明》](../testing/系统说明.md)）消除临时判断；② 对应测试必须进**同一个 PR**；③ 加一条 CI 守卫，断言「每个 `module/*/controller` 至少有一个测试类」。
- **因为**：功能合了、上下文散了，补测试永远不会发生；而项目已有先例证明**能被执行检查的约定才活得下来**（文档链接自检、版本号对齐、types 逐字一致三条都因「有脚本兜着」才没腐烂）。
- **放弃**：只写纪律不加守卫；强制 TDD；单独排一轮「补测试」。
- ⚠️ 已知局限：守卫只验「有测试类」，验不了「断言有没有到点子上」；且它**要等接口层铺满 6 个模块才能打开**，否则一上线就红。
- **来源**：用户追加追问「以后添加新功能的时候如何同步更新测试系统」
- 相关：[ADR 0021](../adr/0021-test-sync-discipline.md)

### D14 · 排版做几何断言；「看排版」进探索任务书

- **决策**：端到端层增加**排版的几何断言**（横向溢出、元素越出可视区、文字被容器裁切），进 CI 门禁；AI 探索任务书增加「**顺手看排版**」一条（审美与层级、遮挡、看不出主次）。
- **因为**：之前把「排版」等同于「视觉回归截图比对」，**这是个错误的概念合并**。排版的**几何事实**是纯数值比较——浏览器直接给出每个元素的矩形框，**不需要基准截图、也不需要 AI 判断**，因此可重复、能进门禁。只有**审美与层级**那半才需要判断力，交给 AI 探索粗筛与人眼。
- **放弃**：维持「排版零自动化、只能靠人眼」的结论（那等于把一做就有的那半也放弃了）。
- ⚠️ 明确不做的仍是视觉回归（三条理由不变），且**不做「元素重叠」检测**（浮层本来就该重叠，会大量误报；误报会让人养成「红了也照合」的习惯），视口只挑 1280 / 768 / 375。
- **来源**：主人追问「ui 排版测试可以交给 AI 探索测试吗」
- 相关：[ADR 0020 Amendment 1](../adr/0020-layered-test-system.md)

### D15 · 探索报告写进 `gitignore` 的本地目录，任务书做成平台无关

- **决策**：报告写到 `.workbuddy/exploration/<日期>-<HHmm>-<短ID>.md`——该目录**已被 `.gitignore` 排除**；若执行方没有这个目录约定，**判据是「写到一个不进 git 的本地目录」**，位置自选但必须在报告开头写明。同时任务书**自包含**：写入「能力自检」一节，缺能力必须**声明**而不是默默跳过。
- **因为**：① 报告描述的是「探的那天系统怎么表现」，代码一改就陈旧——入库等于养一份会过期的真相源，正是 [ADR 0006](../adr/0006-bare-array-import-contract.md) 的失效模式；② 真正值得留的东西**永远有落点**（能固化的写 spec、没定论的进 todo），报告只是草稿；③ 执行探索的 AI **可能来自任何平台**，而 `.codebuddy/rules/` 的自动加载只在部分工具里生效，所以任务书不能依赖它。
- **放弃**：入 `docs/` 新目录（会漂 + 要动文档地图与目录树）；附在 `docs/worklog/` 里（会撑破工作台「只写三类」的边界）；仓库外平级目录（换机器就丢，且没有系统约定支撑）。
- **来源**：主人追问「ai探索之后的报告放哪里」「以后我用来做ai探索的agent可能是其他平台的，能确保正常使用吧」
- 相关：[《测试系统说明》](../testing/系统说明.md)、[`docs/testing/agent-exploration.md`](../testing/agent-exploration.md)

### 本次定下的叫法

**无新增**——五个测试术语（单元 / 接口 / 服务集成 / 端到端 / 探索）都是通用技术词，**不收进 `CONTEXT.md`**（见 D5）。定义钉在 [《测试系统说明》](../testing/系统说明.md)，够用且不污染术语表。
