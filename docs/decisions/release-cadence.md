# 决策日志：发版频率

## 2026-10-05 · 主人提问，一轮问答

起因是主人问「发版频率多少合适，以及每次发版荧是如何知道相较于上次发版有哪些改动的」。先答机制、再谈频率——**先答机制**是因为「怎么知道改了什么」是客观事实，有它才谈得上「多久发一次」。

### 先摸清的机制：四层，从机器信得过到只靠人

1. **真相源是 `git tag`**（[ADR 0015](../adr/0015-version-number-governance.md)）：两个版本之间的**全部**改动 = `git log <上一个tag>..HEAD`，随时可机械列出。
2. **给人读的是 `CHANGELOG.md`**：改动落地时随手写进 `[Unreleased]`，发版时固化成 `## [x.y.z] - 日期`。
3. **门禁会验这一段**：`scripts/check-version.sh` 断言 CHANGELOG 里存在 `## [<版本号>]` 段（还有三处手写点对齐、lockfile 未漂、compose 用 `${APP_VERSION}`）。**「忘了写 CHANGELOG」是发不出去的**——`release.yml` 停在第一个 job，构建与部署根本不跑。
4. ⚠️ **但门禁只验「那一段存在」，验不了「内容写全」**：两个 tag 之间改了东西却没记进 `[Unreleased]`，发版照样能过。**这是唯一只靠人的地方**，也是荧每次发版前会用 `git log --oneline <上一个tag>..HEAD` 逐条对账、补漏记的原因。

### 再谈频率：现状与三类不对称成本

现状（`CHANGELOG.md` 的日期）：`1.0.0` 09-26 → `1.1.0` 10-01 → `1.2.0` 10-03 → `1.3.0` 10-04 → `1.3.1` 10-05 → `1.3.2` 10-05，**9 天 6 个版本、最后一天连发两个**。

发版边际成本确实极低（人只敲 `git tag && git push`，四步全自动、有回滚脚本），但三类成本不对称：**迁移不可回滚**（回滚只换镜像、不换 schema）、**镜像在各处堆积**、**一天连发多次会让「哪次引入的」变难定位**。结论是约束频率的是 schema 变化与可定位性，不是构建时间。

### D1 · 按风险分三档，不按日历

- **决策**：① 修 bug / 纯前端 / 无迁移 → 随时发，不设上限；② 带 DB 迁移（向后兼容）→ 一周 1～2 次或每个里程碑一发；③ 破坏性变更 / 大功能 → 单独发一次。配套：迁移与代码拆开发、tag 不当存档点、`[Unreleased]` 不放过久。全文见 [ADR 0023](../adr/0023-release-cadence-by-risk.md)。
- **因为**：推荐的正是这一档方案，主人采纳。前三个备选各自漏一角——日历制会让「修好了但线上还坏着」白白延长、且不解决观察期；完全临场判断在开发节奏快时会退化成没判断（一天连发两次已经出现过）；「只在有迁移时守规矩」漏掉破坏性变更这一档（它常常不带迁移）。
- **放弃**：① 固定日历发版；② 不定规矩（现状）；③ 只在有迁移时才守；④ 加一套 staging / 预发布环境（与本机 dev 形态重复，且与 [ADR 0010](../adr/0010-china-mirrors-for-build-deps.md) 「不在 CI 之外维持等价环境」的取向冲突）。
