# 决策日志：「关于」功能与版本号治理

## 2026-10-01 · 三轮 grill

起因是「增加一个关于的功能，里面要展示当前版本号」。开问前先摸了仓库，三条事实决定了整棵树的形状：

1. **「当前版本号」在这个仓库里是四个不同的数**：`git tag` 是 `v1.0.0`（且 `HEAD` 已领先它 4 个提交），
   `package.json` 是 `0.1.0`，`pom.xml` 是 `0.1.0-SNAPSHOT`，compose 的镜像 tag 是写死的 `0.1.0`。
   而 `CHANGELOG.md` 早已明文规定「版本号以 `git tag` 为准，包版本与发布版本无关」——
   所以**前端直接显示 `0.1.0` 是跟项目自己的公约打架**。
2. **没有任何通道能把版本号送进前端**：`vite.config.ts` 无 `define`，两个 Dockerfile 唯一的 `ARG`
   都是换源用的，后端无 actuator 也无版本接口。这条通道得从零造。
3. **两个 `.dockerignore` 都排除 `.git/`** → 容器里跑不了 `git describe`；且 CI 的 `checkout`
   没配 `fetch-depth: 0`，浅克隆拿不到 tag。版本号只能在构建前算好再传进去。

相关：[ADR 0015](../adr/0015-version-number-governance.md)

### D1 · 版本号以 `git tag` 为准，改称谓不改机制；顺手统一三处手写点

- **决策**：`git tag` 是唯一真相源；`package.json` / `pom.xml` / compose 的 `image` 是它的手写镜像，
  靠 `scripts/check-version.sh` **在打 tag 时**校验；镜像 tag 跟随版本号。
- **因为**：采纳推荐。`CHANGELOG.md` 已经有这条公约，本轮只是给它加一条可执行的门禁。
  第 4 问答「顺手一起做」时用户选了范围更大的方案（与推荐相反），于是把连锁影响完整问了一遍。
- **放弃**：① 引入根目录 `VERSION` 文件作单一来源 + 脚本回写三处（Maven 要用 CI-friendly
  `${revision}`，牵动坐标与 `mvn install` 语义）；② 只对齐 `package.json`，compose 与 pom 不动；
  ③ 镜像 tag 保持写死 `0.1.0`（放弃了这个改动唯一的实收益）。
- **来源**：Q4、Q5、Q9、Q10

> **Q4 - 本次要不要顺手把「版本号统一」一起解决？**
> 选项：不顺手做 / 做一半（只对齐 `package.json`）/ 顺手一起做。
>
> ➡️ 我推荐「不顺手做」，理由是它会把「加一页」变成「改发布流程」。
>
> **你的回答**：顺手一起做 —— 与推荐相反，因此引出第 2 轮整整四个问题。

> **Q5 - 统一之后「版本号」的家安在哪、镜像 tag 怎么处理？**
> 选项：手写对齐 + CI 门禁（镜像 tag 跟版本）/ 手写对齐（镜像 tag 不动）/
> 引入 `VERSION` 文件 + 脚本回写 / 只对齐 `package.json`。
>
> ➡️ **推荐「手写对齐 + CI 门禁，镜像 tag 跟版本」**。校验放在 `on: push: tags` 上恰好绕开
> 「HEAD 常领先 tag」这个必然状态；镜像 tag 跟版本是「一起做」里唯一有实收益的一项——
> 每个已发版本各留一份镜像，回滚不必重新构建。
>
> **你的回答**：按推荐

> **Q9 - `pom.xml` 的版本写成什么样？**
> 选项：保留 `-SNAPSHOT` / 改成纯 `1.1.0` / pom 不管。
>
> ➡️ **推荐保留 `-SNAPSHOT`**。它的含义正是「这个坐标还没发布过」；写死成 `1.1.0` 会让两次发版
> 之间的 `mvn install` 用未发布代码覆盖 `~/.m2` 里的正式坐标。校验时剥掉后缀即可。
>
> **你的回答**：按推荐

> **Q10 - 镜像 tag 用什么字符串？**
> 选项：纯版本号 `1.1.0` / 带 `v` 的 `v1.1.0` / 版本 + commit / 版本 + 时间戳。
>
> ➡️ **推荐纯版本号**。`版本 + commit` 的粒度最细，但它**和 compose 的字面量约束直接冲突**：
> `image:` 必须是确定字符串，塞 commit 就只能改成 `.env` 变量替换，而 `.env` 已被 ADR 0011
> 划给密钥。刻意让 `git tag`（带 `v`）与镜像 tag（不带 `v`）字面不同，还能少混。
>
> **你的回答**：按推荐

### D2 · 版本号经构建参数注入，不新增接口

- **决策**：`scripts/deploy.sh` 从 git 算出四个值 → 由它 `export` → compose 的 `build.args`
  → Dockerfile → 前端 `vite define` 成 `__APP_*__` 常量、后端进 `ENV QUIZZY_VERSION`。
- **因为**：采纳推荐。nginx 只发静态产物，运行时没有注入点；构建期注入零运行时成本、不用新增接口，
  与 ADR 0013「CI 只做门禁、上线由人跑 `deploy.sh`」的形态最贴。
- **放弃**：① 后端加 `GET /api/meta` 运行时拉（唯一好处是能分开展示前后端版本，代价是多一个接口
  加后端一条独立注入通道）；② Vite 直接读 `package.json`（读到的是 `0.1.0`，且构建后文件根本不在产物里）；
  ③ 前端常量文件硬编码（多一个「改版本号要记得改这里」的地点）。
- **来源**：Q2、Q8

> **Q2 - 这个值怎么进到前端？**
> 选项：构建期注入 / 后端 `GET /api/meta` / Vite 读 `package.json` / 前端常量硬编码。
>
> ➡️ **推荐构建期注入**。代价是 dev 直跑时拿不到 build-arg，需要显式退化（Q7 副行与
> `dev` 兜底就是为它准备的）。
>
> **你的回答**：按推荐

> **Q8 - 范围边界画在哪？**（`OpenApiConfig.java:15` 还有个写死的 `.version("v1")` 会显示在 swagger UI 上，
> 而 `README` 里的「v1」是产品代次）
> 选项：都收 / 只收后端 API 版本 / 只收文档术语 / 到此为止记 TODO。
>
> ➡️ **推荐都收**。那处 `.version("v1")` 现在是个**错值**（产品代次占了 API 版本的位置）；
> 既然已经为前端造了 build-arg 通道，后端复用是同一条通道的顺手事。
>
> **你的回答**：按推荐

### D3 · 「关于」是弹窗，显示 tag 主行 + 领先信息副行

- **决策**：顶栏用户区「退出」旁加「关于」按钮 → `el-dialog`；内容 = 产品名 + 版本主行（tag 字面）
  + 副行（仅 `HEAD` 领先 tag 时出现：`+N 提交 · 短 sha`）+ 构建时间 + 仓库地址 + MIT 许可。
- **因为**：采纳推荐。导航位该留给高频动作；「关于」与「退出」同属系统级操作；项目已有 4 个
  `el-dialog` 统一 `visible` / `update:visible` 模式，可直接复用，零新依赖。
- **放弃**：① 侧栏加第 6 项做独立路由页（低频信息占主导航）；② 侧栏底部常显小字（版号随手可见，
  但若诉求正是这个它反而更贴——留作用户可选项）；③ 顶栏用户名改下拉菜单（要新建下拉组件，改动面更大）。
- **来源**：Q1、Q3、Q7

> **Q1 - 「当前版本号」到底指哪个字符串？**（`HEAD` 已领先 `v1.0.0` 四个提交，本次要加的「关于」
> 功能本身并不在 `v1.0.0` 里）
> 选项：只显示 `v1.0.0` / tag 主行 + 领先信息副行 / 完整 `git describe` 一行 / `package.json` 的 `0.1.0`。
>
> ➡️ **推荐「tag 主行 + 副行」**。tag 是项目钦定的真相源，当主行；但单显示它等于撒谎——
> 你的代码里有 tag 里没有的东西。把「领先几个提交 + 确切 commit」放副行，既诚实又不用看乱码。
>
> **你的回答**：按推荐

> **Q3 - 「关于」放哪、什么形态？**
> 选项：顶栏按钮 + 弹窗 / 侧栏底部常显小字 / 侧栏新增路由页 / 顶栏用户名下拉菜单。
>
> ➡️ **推荐顶栏按钮 + 弹窗**。
>
> **你的回答**：按推荐

> **Q7 - 弹窗里除了版本号还显示什么？**
> 选项：极简 / 标准（+ 构建时间、仓库地址、MIT 许可）/ 丰富（+ 技术栈、运行环境）/ 标准 + 数据说明。
>
> ➡️ **推荐「标准」**。构建时间在有无 tag 时都在，能保证弹窗不空；`丰富` 里的技术栈会随依赖升级
> 腐化（正是 ADR 0006 要防的那种「会复制的易变事实」）；`数据说明` 涉及对外承诺，不硬塞未经确认的说法。
>
> **你的回答**：按推荐

### D4 · 打 `v1.1.0`，并取消「v1 产品代次」这个说法

- **决策**：本次完成后打附注 tag `v1.1.0`（新功能 → SemVer MINOR）；`README` / `scope.md` 里的
  「v1」改为直白的范围描述，`CONTEXT.md` 只补「版本号」一个词，`CHANGELOG` 那张四行表缩到三行。
- **因为**：采纳推荐。不打 tag 的话三处只能对齐到已经过时的 `1.0.0`，等于把漂移固化；
  「产品代次」这个概念只是为了解释一个命名意外而存在，**删掉意外比给它上户口便宜**。
- **放弃**：① 打 `v1.0.1`（新增功能应为 MINOR）；② 不改名，只在术语表里把「产品代次」正典化；
  ③ 改名成「第一代」（暗示后面真有个第二代要交付）。
- **来源**：Q6、Q11

> **Q6 - 本次改动完成后要不要打新 tag？**
> ➡️ **推荐 `v1.1.0`**。这也让 Q1 的副行设计得到验证点：正常发版后副行**自然消失**，
> 只有 dev / 未发版状态才出现——副行从此是「你不在发布版本上」的提示，而不是噪声。
>
> **你的回答**：按推荐

> **Q11 - 「v1 产品代次」这个说法怎么处置？**
> 选项：取消这个说法 / 改名「第一代」/ 保留并补术语条目 / 只改 `OpenApiConfig`。
>
> ➡️ **推荐取消**。
>
> **你的回答**：按推荐

### D5 · 旧镜像等新镜像验证通过后再删

- **决策**：重新部署并确认「关于」显示正确之后，才 `docker rmi quizzy-server:0.1.0 quizzy-web:0.1.0`；
  只删这两个 tag。
- **因为**：用户选了「全部删掉」。但摸环境时发现**两份旧镜像正被运行中的容器引用**，
  直接 `docker rmi` 必然报 `image is being used by running container`；而且删掉旧镜像就失去了
  改造前「最后一份确定能跑的东西」这个退路。顺序因此被定为：先部署新的、验证通过，再删。
- **放弃**：① 先留着不动；② 把旧镜像重新打成 `1.1.0`（直接排除——那镜像里的代码不含本次改动，
  叫 `1.1.0` 是错值）。
- **来源**：Q12

> **Q12 - 本地旧镜像 `quizzy-server:0.1.0` / `quizzy-web:0.1.0` 怎么处置？**
> ➡️ 我推荐先留着不动并说明了理由，同时注明「删镜像属于破坏性操作，没有明确确认我不会执行」。
>
> **你的回答**：全部删掉
>
> **后续处理**：确认删除，但把执行时机挪到新镜像验证通过之后，并把「只删这两个 tag、
> 不碰基础镜像与 `mysql:8`」写成硬约束。

## 未决
