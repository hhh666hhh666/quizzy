# 决策日志：给 quizzy 加移动端与微信小程序

## 2026-10-03 17:16 · 第 3 次 grill

起因是「想让这套系统可以给手机用」，随后用户补了两条硬约束：**小程序将来确定会做**，且**PC 端与移动端有各自不同的页面风格优化**。

开问前先派了两个只读调研，摸到三条关键事实：

- 后端是**纯无状态 Bearer JWT**，所有接口在 `/api/**`、无 context-path、无 session / cookie / CSRF——多客户端复用可行性最好的一点。
- **一个真实缺口**：`docs/requirements/scope.md:35` 与 [ADR 0017](../adr/0017-public-signup-service.md) 都写了「公开注册带图形验证码与按 IP 限流」，但**后端代码里完全没实现**（全仓搜 `captcha|RateLimit|@WebFilter` 零命中）。
- `docs/todo/`、`docs/design/前端.md`、`docs/requirements/scope.md` 里**都没有**移动端/小程序线索，是干净起点。
- 另核实：后端 `QuizStartDTO.sourceType` 支持 `PAPER / QUICK / WRONG_BOOK`，`QuizService.start` 对 PAPER 校验 `paper.ownerId == userId`——「从已有试卷开始答题」技术上现成可用。

本轮同时跑了 domain-modeling，结论是**不新增术语**（见 D10）。

### D1 · 移动 H5 与小程序用 uni-app 单工程

- **决策**：用 **uni-app（Vue3）单工程**，一套代码编译出 H5 与微信小程序，差异走条件编译。仓库新增顶层目录 `quizzy-mobile`。
- **因为**：后端要复用、团队现栈是 Vue3，且移动端与小程序风格接近——这样只需维护两套前端（PC 一套、移动一套）而不是三套。
- **放弃**：① 原生小程序（WXML）+ 另写独立 H5——双份维护；② Taro——同为跨端方案，但贴合度不如 uni-app。
- **来源**：Q1
- 相关：[ADR 0019](../adr/0019-mobile-clients-with-uniapp.md)

> **Q1 - 技术选型：移动 H5 与小程序用什么搭？** (a) uni-app（Vue3）单工程，一套代码编译出 H5 与微信小程序，差异处用条件编译；(b) 原生小程序（WXML/WXSS）+ 另写一个独立 H5(Vue)；(c) Taro(React)。
>
> ➡️ 选 (a) uni-app。代价：Element Plus 在 uni-app/小程序里用不了，移动端组件要换 uni-ui / uView 一类。
>
> **你的回答**：其他按你推荐的来（= a）

### D2 · PC 端 `quizzy-web` 完全不动

- **决策**：PC 端保持 Vue3 + Element Plus，一个字不重写。移动端是**全新工程、全新移动设计**，不是把 PC 页面压窄。
- **因为**：用户已明说 PC 与移动风格不同；把响应式塞进 `quizzy-web` 等于让一个工程同时背两种设计语言，条件样式会迅速腐烂。
- **放弃**：把 `quizzy-web` 改造成「PC + 响应式」双风格。
- **来源**：Q2
- 相关：[ADR 0019](../adr/0019-mobile-clients-with-uniapp.md)

> **Q2 - 现有的 PC 端（`quizzy-web`）动不动？** (a) 完全不动；(b) 把 `quizzy-web` 改造成「PC + 响应式」双风格。
>
> ➡️ 选 (a) PC 完全不动。
>
> **你的回答**：其他按你推荐的来（= a）

### D5 · 移动端只做「消费」

- **决策**：移动端/小程序只做**消费**——刷题、快速练习、错题本、答题记录；「建设」（题库增删改查、组卷、Excel 导入导出）留在 PC。
- **因为**：支撑硬事实——Excel 导入是 multipart 上传、导出是流式附件下载，在**小程序里体验很差甚至不可行**；手机做批量建题本来就反人性。
- **放弃**：移动端功能对齐 PC。
- **来源**：Q5
- 相关：[ADR 0019](../adr/0019-mobile-clients-with-uniapp.md)

> **Q5 - 移动端的功能裁剪：只做「消费」还是也做「建设」？** (a) 只做消费（刷题 / 快速练习 / 错题本 / 记录），建设留 PC；(b) 对齐 PC。
>
> ➡️ 选 (a)。
>
> **你的回答**：其他按你推荐的来（= a）

### D6 · 登录先复用现有账号密码接口

- **决策**：移动端与小程序先复用 `POST /api/auth/login`（用户名密码 + 无状态 Bearer JWT）。微信登录（`wx.login → code2session → 账号绑定`）**后置**，另立一项。
- **因为**：复用意味着后端**零改动**；微信登录要加 AppID/Secret、绑定关系、账号合并，属新后端能力。
- **放弃**：小程序直接上微信登录。
- **来源**：Q6
- 相关：`docs/todo/2026-10-03-TODO-微信登录与账号绑定.md`

> **Q6 - 移动端与小程序怎么登录？** (a) 先用现有 `/api/auth/login`，微信登录后置；(b) 小程序直接用微信登录。
>
> ➡️ 选 (a)。
>
> **你的回答**：其他按你推荐的来（= a）

### D7 · 「图形验证码 + IP 限流」作为独立工作项排上

- **决策**：把公开注册承诺的**图形验证码 + 按 IP 限流**缺口作为**独立工作项**排期，与移动端并行，**优先于小程序上线**。
- **因为**：代码里完全没有实现，而站点已对公网开放运行；多开一个公网小程序会把滥用面再放大一层。它是「公开服务」的欠账，不该拖到小程序上线时才想起。
- **放弃**：只在 TODO 记着、不排期。
- **来源**：Q7
- 相关：`docs/todo/2026-10-03-TODO-注册风控.md`（**不进 ADR 0019**——ADR 0017 已定门槛，这是实现欠账，不是新决策）

> **Q7 - 「图形验证码 + IP 限流」这个承诺缺口怎么办？** (a) 本轮就作为独立工作项排上（优先于小程序上线）；(b) 只在 TODO 里记着。
>
> ➡️ 选 (a) 排上，与移动端并行。

### D8 · H5 走同域子路径 `/m/`

- **决策**：移动 H5 部署在 `https://域名/m/`，与 PC 站同一域名。因此**不新增 CORS 配置**。
- **因为**：后端 `quizzy.cors.allowed-origins` 当前**默认为空**（靠同源部署生效）；同域即免跨域。小程序不受此约束（它认的是微信合法域名白名单）。
- **放弃**：独立子域（如 `m.域名`）——更干净但要动 CORS 与证书配置。
- **来源**：Q8
- 相关：[ADR 0019](../adr/0019-mobile-clients-with-uniapp.md)

> **Q8 - H5 部署形态：同域子路径还是独立子域？** (a) 同域不同路径（`/m/`）；(b) 独立子域。
>
> ➡️ 选 (a) 同域子路径，零 CORS 改动。
>
> **你的回答**：其他按你推荐的来（= a）

### D9 · 备案是外部前置（域名已有、尚未 ICP 备案）

- **决策**：接受「域名已有但**尚未 ICP 备案**」为外部约束；把它显式记入 TODO 并作为**小程序上线的门禁**。境内服务器上 H5 与小程序**都**要等备案 + HTTPS；小程序另需微信「request 合法域名」白名单。
- **因为**：它不受代码进度控制，最容易被拖；且一旦被遗忘会卡住整个上线。**不卡仓库侧文档与工程搭建，只卡上线。**

> **Q9 - 域名 / ICP 备案 / HTTPS 现在什么进度？** (a) 已备案且证书能签发；(b) 域名有了但还没备案；(c) 都还没开始。

### D11 · 「消费」边界包含「选已有试卷开始答题」

- **决策**：移动端加一个**只读的试卷列表**（`GET /api/papers`）+ 点进去开始答题（`sourceType: 'PAPER'`），但不做新建 / 编辑 / 删除。
- **因为**：PC 组卷、手机做题是很自然的诉求；后端与 `startQuiz({sourceType:'PAPER', paperId})` 都已就绪，只多一个只读列表页，成本很低。
- **放弃**：移动端只留「快速练习 + 错题重练 + 继续未完成会话」，试卷严格属 PC。
- **来源**：Q11

### D13 · 移动 H5 不做 PWA

- **决策**：不引 manifest / Service Worker，H5 就是「浏览器里能用」；类 App 体验交给小程序。
- **因为**：PWA 与小程序在「类 App 体验」上功能重叠；且微信内置浏览器**不支持 PWA 安装**。避免为同一目标维护两套安装机制。
- **放弃**：H5 也做成可安装 PWA。
- **来源**：Q13
- 相关：[ADR 0019](../adr/0019-mobile-clients-with-uniapp.md)

> **Q13 - 移动 H5 要不要顺带做成 PWA？** (a) 不做；(b) 做。
>
> ➡️ 建议 (a) 不做。若将来发现有人想在微信外频繁用，再加 manifest 也只是半天的事。
>
> **你的回答**：都按推荐的来（= a）
