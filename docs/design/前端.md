# 前端

**目的**：讲清页面的组织方式、状态与服务端数据怎么流转，以及哪些边界容易踩。

**读者**：要改前端的人。

**真相源**：**路由、页面清单、组件清单以代码为准**（`quizzy-web/src/` 下的 `router/`、`views/`、`components/`、`stores/`、`api/`）。本文档只讲边界与约定，不复制那些清单。

---

## 页面流与信息架构

一条主线：登录 → 挑题（题库 / 组卷） → 答题 → 看结果 → 回头练错题。

- **题库**：题目的列表与维护入口，也是导入导出的入口
- **试卷**：固定卷与规则卷统一管理，规则卷可以在出卷时预览抽题
- **答题**：一次会话的作答界面，逐题推进，即时反馈
- **结果**：会话结算后的逐题回顾
- **历史**：会话列表，未完成的可以继续作答
- **错题本**：错题列表与一键错题重练

题库与试卷的编辑在抽屉里完成，不占独立路由。

## 路由与访问控制

路由定义见 `router/index.ts`。除登录注册外的路由需要登录态，由**路由守卫**统一拦截，token 存在 Store 里并做了持久化。

注意：路由守卫只挡「没登录」，**不挡「没有数据权限」**——后者由服务端判定（见 [《API》](API.md) 的数据边界一节）。

## 页面与组件边界

- 页面组件按上面的路由划分，放在 `views/`
- 可复用组件放在 `components/`，其中 Markdown 渲染是重点：题干、选项、解析都是 Markdown，渲染器负责代码块高亮
- 类型定义集中在 `types/`，应与后端 VO 对应；**它不是独立契约源**，后端结构变化时以 springdoc 输出为准

## 状态与 API 访问

- Store 放全局状态：用户信息与 token（持久化）、当前会话状态。定义在 `stores/`
- HTTP 封装在 `api/request.ts`，统一处理 baseURL、token 注入、错误提示与响应解包
- 各领域的请求按模块拆分到 `api/` 下对应文件，不散落在组件里

## 构建与类型检查

前端**只有类型检查与构建两个门禁**，没有单测也没有 lint（`package.json` 里没有这两个 script）。

⚠️ `vite build` 走 esbuild 只剥离类型、不做检查，所以**类型错误只会被 `typecheck` 挡住，构建永远是绿的**。别以为构建过了就是好的。详见 [../testing.md](../testing.md)。
