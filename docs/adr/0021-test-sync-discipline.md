# 新功能与它的测试同 PR 落地，并用一条机械守卫兜底

Status: accepted

测试系统的价值取决于「新功能有没有配测试」，而这件事最容易被无声跳过——功能合了、上下文散了，补测试永远不会发生。所以把它从「靠记性」改成两条硬约束：

1. **映射表 + 同 PR 规则**：改了什么就补哪层，由一张表决定（表在 [《测试系统说明》](../testing/系统说明.md)），不靠临时判断；对应测试必须进**同一个 PR**，不许「先合功能、测试下轮补」。
2. **机械守卫**：新增脚本，断言「每个 `module/*/controller` 至少有一个对应的测试类」。它把「新模块配了测试」从约定变成**可验证事实**——照 `ci.yml` 里 `types` 镜像 `diff` 守卫的先例。

选择机械守卫而非只靠纪律，是因为这个项目已经证明**能被执行检查的约定才活得下来**：文档链接自检、版本号对齐、types 逐字一致，三条都因为「有脚本兜着」才没腐烂。

## Considered Options

- **只写纪律、不加守卫**：文档写得再清楚，漏了也不会有任何信号——`docs/testing` 的「已知盲区」已经这么躺了很久。
- **强制 TDD（先写测试再写实现）**：实现前就要把断言写准，对探索期的接口设计是负担；本项目单人开发、接口还在演进，收益不抵摩擦。
- **单独排一轮「补测试」**：上下文已经散了，补出来的测试往往只覆盖「当时想到的」，且这一轮永远会被别的事挤掉。
- **守卫做到「检查断言质量」**：静态检查读不出断言好坏，做不到；退一步只验「存在」，边界明写在下面。

## Consequences

- 新脚本加入 `ci.yml` 的文档/门禁 job 序列。**它会先红**——现有 6 个模块里只有 2 个有测试类，所以守卫要等接口层铺满才能打开，这件事记在 `docs/todo/2026-10-04-TODO-测试系统落地.md`。
- 守卫的**已知局限：只验「有测试类」，验不了「测试有没有断言到点子上」**。它是防遗忘的兜底，不是质量保证——质量仍由评审与「改动 → 补哪层」那张表兜。
- 因为文档**从不列测试清单与数量**（数量会变，清单必然漂），所以**加测试本身不需要改任何文档**。这是刻意的：把同步负担压到最低，同步纪律才能真正被执行。
- 「只改样式 / 文案 / 排版」明确**不需要**补测试（不写新断言）。⚠️ 这不是因为「排版没人测」——排版的几何事实由端到端层的断言覆盖，改到已覆盖的页面会自动被检到；**只有审美与层级**那半靠人眼与探索粗筛，见 [ADR 0020 Amendment 1](0020-layered-test-system.md)。
- 引入**新的一层、新的端、新的运行环境**属于系统变更，必须走一条新 ADR，**不许在功能 PR 里顺手加**。
- AI 探索测试撞到的 bug，必须**回写成一条 spec** 才算收尾——否则下次不一定还能撞到，坑会反复踩。探索测试的定位见 [《测试系统说明》](../testing/系统说明.md)。

相关：[ADR 0020](0020-layered-test-system.md)（分层与各层边界）、[ADR 0006](0006-bare-array-import-contract.md)（文档不复制会漂的事实）、[ADR 0014](0014-ai-discipline-in-repo.md)（把纪律写进仓库并自动加载）。

## Amendment 1（2026-10-04）：守卫已打开，并正反向验过

正文 Consequences 预告的两件事都落地了：

- 脚本是 `scripts/check-module-tests.sh`，挂在 `ci.yml` 的 `docs` job 上（那个 job 只需要
  bash + git + grep + find，不需要任何 toolchain，几秒跑完）。
- **现有 6 个模块（auth / category / paper / question / quiz / wrongbook）全部铺上了测试**，
  所以守卫现在就是绿的——正文里「它会先红」那句只适用于刚落地的那一刻。

⚠️ 补一条正文没写的**验收要求**：这类检查脚本必须**正反两向**打过。落地时的做法是——
正向：6 个模块全 ok、退出码 0；反向：临时造一个「只有 Controller、没有测试类」的模块 `zzprobe`，
守卫必须报 `MISSING` 并退出码 1（验完即删）。**只跑正向的守卫等于没验**——
它可能只是永远返回成功而已。

已知局限不变：**只验「有没有」，验不了「断言到没到点子上」**。
