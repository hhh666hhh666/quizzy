# 发版频率跟着风险走，不跟着开发速度走

Status: accepted

本项目的发版成本极低：推一个 `v*` tag，[release.yml](../../.github/workflows/release.yml) 依次跑完版本门禁 → 迁移重放 → 构建推 ACR → SSH 部署，人只敲两条命令，出事还有 `server-rollback.sh`。正因如此，实际节奏变成了「改完、CI 绿、就发」——`1.0.0`（09-26）到 `1.3.2`（10-05）**9 天 6 个版本**，最后一天连发两个。这个节奏不必被收成日历制，但也**不能只靠临场判断**：约束发版频率的从来不是构建时间，而是 schema 的变化与「坏了能不能定位到哪一次」。三类改动的成本互不对称：

| 改动性质 | 回滚能不能兜住 | 说明 |
|---|---|---|
| 纯前端 / 纯逻辑 | **能** —— 换个镜像 tag 即可 | 表结构不动，回滚是干净的 |
| 带 DB 迁移（向后兼容） | **不能** —— 回滚只换镜像、不换 schema | [ADR 0016](0016-cloud-deploy-with-release-pipeline.md) 明说破坏性迁移不能靠回滚兜底：迁移一旦跑过，旧镜像未必还认这张表 |
| 破坏性变更（改判分规则、改接口契约等） | 能回滚，但**难定位** | 它常常**不带**迁移，却改变既有行为 |

另两条次要成本：每个版本在 ACR 与服务器上**各留一份镜像**（磁盘会持续长，见 [那条待办](../todo/2026-09-20-TODO-运行与运维.md)）；部署是一次容器 Recreate，**有短暂中断**——自用工具影响小，但服务对公网开放（[ADR 0017](0017-public-signup-service.md)），仍是用户可见的。

所以规则按**改动性质**分三档，不按日历：

1. **修 bug / 纯前端 / 无迁移** —— 随时发，不设上限（当天发也行）。
2. **带 DB 迁移、但向后兼容** —— 攒一攒，一周 1～2 次，或每个功能里程碑一发，让迁移有一段观察期。
3. **破坏性变更 / 大功能** —— 单独发一次，前后不夹别的改动。

配套三条做法：

- **迁移与代码尽量拆开发**：迁移先发一次（只加表 / 加可空列，向前兼容），逻辑后发。这样「回滚代码」仍然安全，第 2 档的观察期也才有意义。
- **tag 不是存档点**：`git push origin vX` 就是部署到线上，没有「先打个 tag 不发」这回事。要存档用分支或 `CHANGELOG`。
- **`[Unreleased]` 不放过久**：超过两三周没发就专门发一次——线上版本离仓库越远，回滚落点越远、线上问题越难复现。

## Considered Options

- **固定日历发版**（每周 / 每两周一次）：把「什么时候发」从判断变成日历，最省心。但它把已修好的东西压在手里等下一个窗口，而本项目发版成本低、使用者就是维护者本人——等于白白延长「修好了但线上还是坏的」那段时间；而且它不解决真正的约束（迁移没有观察期）。
- **不定规矩、一切临场判断**（现状）：最灵活。但一天连发两次已经出现过，说明开发节奏一快，「临场判断」会退化成「没判断」；而迁移那件事**没有兜底**——现在没出事只是还没赶上。
- **只在有迁移时才守规矩**（无迁移不限、有迁移攒一周）：最接近采用方案，但漏了第 3 档——破坏性变更往往**不带**迁移，一样需要单独发。
- **加一套 staging / 预发布环境，先验再发**：能真正压低发布风险。但本机 `docker-compose.dev.yml` 已承担开发形态（[ADR 0007](0007-dev-prod-compose-with-bind-mount.md)），再维持一套等价环境要多担一份配置与一个漂移源，与 [ADR 0010](0010-china-mirrors-for-build-deps.md)「不在 CI 之外再维持一套等价环境」的取向冲突。放弃。
- **采用方案**：按风险分三档 + 三条配套做法。

## Consequences

- 发版前多了一次自问「这次改动属于哪一档」，不需要记日历。⚠️ 这条规矩**没有机械守卫**——没有任何脚本能判断「这次该不该现在发」，它与 [ADR 0020](0020-layered-test-system.md) 把「审美与层级」划给人眼同类：**能被机器守住的只有 [ADR 0015](0015-version-number-governance.md) 那套版本号一致性**（含「CHANGELOG 里必须有对应版本段」，它管的是「发得出去发不出去」，不是「该不该发」）。
- 「带迁移的发版要留观察期」把**迁移与逻辑拆开**变成默认动作，于是**一次发版不再是一个大杂烩**：发版切分变细，版本号增长会比以前更快。这是刻意的取舍——用版本号数量换可定位性。
- 本决策**不改任何代码、不改任何流水线**：`release.yml` 的触发条件与四步顺序一个字不变，变的只是「人什么时候去推那个 tag」，所以它没有测试，只有判断。
- 操作步骤不在本文复制：上线动作仍以 [《部署》](../operations/deployment.md) 与其上线前检查清单为准——其中已新增一条「节奏自检」，把上面三档压成发版前的一句自问。
