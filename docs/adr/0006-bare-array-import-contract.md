# JSON 导入契约取裸数组

Status: accepted

`POST /api/questions/import/json` 收的是题目对象的**裸数组**，不带 `{"questions": [...]}` 外壳。裸数组的好处是文件即一屏题目、diff 干净、整段粘进导入框不用先剥一层壳；配套 skill `md-to-question-bank` 生成的题库文件也已经按裸数组产出。

## Considered Options

- **包装对象**（原 `DESIGN.md` 的 JSON Schema 最初写的是这个）：对未来加元信息友好，但对当前唯一的使用方式（人眼看、整段粘贴）只是噪音。
- **两者都收**：看似两全，实际是为一个内部工具维护两套解析路径，收益远小于成本。

## Consequences

- 原根目录 `DESIGN.md` 的 JSON Schema 一节原本写的是包装对象，与实现不一致，已改为裸数组（该文件后续已删除，见 git 历史；现在的契约写在 [《导入导出》](../design/导入导出.md#json-契约)）。**文档与代码冲突时以代码为准，并同步改文档**，不要靠记忆区分。
- 将来要给导入文件加元信息（来源文档、生成时间、批次号）时，必须改成包装对象，并同时改 skill 的输出格式——那是一次破坏性变更，做之前先回来把这条 ADR 置为 superseded。

## Amendment 1（2026-10-06）：元信息走**查询参数**，不改回包装对象

正文 Consequences 第 2 条预测「将来要给导入文件加元信息时必须改成包装对象」。2026-10-06 设计「导入时顺带建一张试卷」（见 [ADR 0026](./0026-question-set-reuses-paper.md)）时，这个预测**被更正**。

**更正后的做法**：元信息不进 body，改由**查询参数**承载——JSON 那条是 `POST /api/questions/import/json?paperTitle=<标题>`，Excel 那条走 `multipart/form-data` 的普通表单字段。正文的**主决策不变**：`POST /api/questions/import/json` 的 body 仍然是**裸数组**。

**为什么**：包装对象的价值是「让元信息与题目共处一个 body」，代价是契约破坏、且要连带改仓库外 `md-to-question-bank` skill 的输出格式。而这次要传的元信息（「本次导入要不要顺手建一张卷、卷叫什么」）本就是**对这次导入的附加指令**，与「题目内容」是两回事——放进查询参数，语义与位置是匹配的，且零破坏。

**正文那条预测什么时候仍然成立**：当元信息是**逐题级**（如每道题各自的来源页码）、或体量大 / 需要嵌套结构时，查询参数就不合适了——那时仍按正文写的走包装对象，并回来把正文置为 superseded。
