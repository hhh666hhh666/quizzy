# 头像存进数据库，默认头像由前端生成

Status: accepted

账户自助这轮要加「改头像」。而项目此前**没有任何文件存储基础设施**——没有对象存储 SDK、没有上传落盘、后端与 web 容器都没有持久化卷、备份脚本只备份数据库。为一个头像新开一条存储线不划算，于是把头像以 base64（data URL）直接存进 `user.avatar` 一列；该列为 NULL 时代表「用默认头像」，由前端按用户 id 生成一个 GitHub 风格的 5×5 对称方块。

## Considered Options

- **存服务器本地磁盘 + 给容器加持久化卷**：被否，因为要同时改部署脚本与备份流程，否则容器一重建头像就没——而「备份只备库」这个现状会让这件事**悄悄**出问题。头像丢了不会有任何报错。
- **阿里云 OSS**：与已定的「备份上 OSS」同一条路，但要引 SDK、在 `.env` 里管 AccessKey、配 bucket 权限，等于单独立一个基础设施项目。不是不好，是不该顺带做。
- **不上传，只用生成头像**：零存储。但生成头像只该当默认值，不该是唯一选项——用户想用自己的图是合理的。
- **存进数据库（选定）**：零新增基础设施。

## Consequences

- ⚠️ **`docs/requirements/scope.md` 的「明确不做」必须改**：原文是「图片上传与富文本编辑器」，收窄为「**题目内容里的**图片上传与富文本编辑器」。这条边界当初是为题目内容写的，头像不在它的射程内。
- 头像必须**很小**，所以三处一起收紧：只收 jpeg / png / webp 且**后端按文件头判定**（不信扩展名、不信前端声明）、单张原图上限 2MB、前端上传前压到最长边 ≤256px 再转 webp。**拒绝 SVG**——它可以内嵌脚本。
- `user.avatar` 用 **MEDIUMTEXT**：256px webp 的 base64 可能逼近 TEXT 的 65535 字节上限。
- `GET /api/auth/me` 会带上 `avatar`，也就是每次刷新页面都多拉几十 KB。目前可接受，**不预先优化**；若将来体积涨上去，再拆成一个独立端点。
- 生成头像的算法在前端，所以将来移动端要显示它时，得把同一段算法复制过去（或届时改成后端出图）。这是把算法放前端的已知代价。
