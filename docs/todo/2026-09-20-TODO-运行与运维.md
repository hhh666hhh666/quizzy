## 2026-10-01 更新：三条定了两条半，新冒出一条

prod 搬到阿里云 ECS（[ADR 0016](../adr/0016-cloud-deploy-with-release-pipeline.md)）后，原来的三条都有了结论：

- **8080 暴露** → **已定：删掉。** nginx 已经反代 `/api`，公网多开一个门没有理由。
  **顺带白捡一个好处**：`nginx.conf` 本来就只转发 `/api/` 与静态资源，`/v3/api-docs`、`/swagger-ui.html`
  落进 SPA 回退——**Swagger 从来没有对外暴露过**，只有直连宿主机 8080 才看得到。所以删掉映射就等于关掉了它，
  既不需要关闭 springdoc，也就不存在「关 Swagger 连带打断 healthcheck」的连锁。
- **日志轮转** → **已定，且 2026-10-02 已落实**：三个服务在 `docker-compose.prod.yml` 里统一限 `max-size: 10m` / `max-file: 3`，不接 logrotate。
  容器日志本来就由 Docker 自己收，接 logrotate 要额外处理 json-file 的路径与信号，成本高于收益。
- **探测端点换 actuator** → **已定：不换**（理由同上：Swagger 没对外暴露，开销仍可接受），[ADR 0012](../adr/0012-healthcheck-probes-api-docs.md) 保持不变。

**新冒出来的一条**：监控。本次只决定上阿里云云监控的基础告警（CPU / 磁盘 / 实例存活），
**应用层指标与日志告警没有方案**——见文末。

## 后端 8080 要不要继续暴露到宿主机

> **已于 2026-10-01 结案：删掉。** 见上文。

`docker-compose.prod.yml` 里 server 有 `ports: 8080:8080`，方便直接开 swagger。纯内网自用没问题。

哪天放到能被别人访问的环境，把这段删掉——nginx 已经反代了 `/api`，不需要后端直接对外。

## 日志没做轮转

> **已于 2026-10-01 结案：在 compose 里配 `logging.options`。** 见上文。

容器日志会一直涨，Docker 默认的 json-file driver 不限制大小。

要么在 compose 里给 `logging.options.max-size`，要么接 logrotate。长期跑下去迟早会吃掉 E 盘。

## 探测端点要不要换成 actuator

> **已于 2026-10-01 结案：不换。** 见上文。

现在 healthcheck 探的是 `/v3/api-docs`，每次探测会真的生成一遍 API 文档（理由见 ADR 0012）。

哪天觉得这点开销碍眼，再引 `spring-boot-starter-actuator` 换 `/actuator/health`。前提是想清楚要暴露哪些端点。

## 应用层监控（2026-10-01 新增）

站点对公网开放之后，「挂了有人会看到」，而现在的可观测性接近于零。

**已经决定的**：上阿里云云监控的基础告警——CPU、磁盘使用率、实例存活。这三条覆盖「机器死了」和「盘满了」。

**没决定的**：应用层的那些——后端 5xx 比例、healthcheck 连续失败、注册量异常突增（垃圾注册的早期信号）、
证书到期时间、备份任务成功与否。可选方向：

- 全部依赖云监控（能覆盖实例与磁盘，但看不到应用内部）
- 给后端加 `/actuator/prometheus` + 阿里云 Prometheus 实例（能力完整，但 2C2G 上再跑一个采集端要算进内存预算）
- 最省的一档：只给「healthcheck 连续失败」和「备份任务失败」加告警，其余靠人偶尔看一眼

**倾向第三档**，理由是 2C2G 的资源预算已经被 MySQL + JVM + nginx 分完了（见 [ADR 0016](../adr/0016-cloud-deploy-with-release-pipeline.md)），
而这两条恰好是「不告警就一定会晚很久才知道」的事。等真的有用户量再说第二档。

## 服务器上的镜像堆积（2026-10-02 新增）

日志轮转已经在 `docker-compose.prod.yml` 里落实（三个服务统一 `max-size: 10m` / `max-file: 3`），
所以**会涨的换成了镜像**——每次部署都从 ACR 拉一份新的，40G 系统盘（已用 7.4G）迟早会被吃满。

**没决定的是**「谁在什么时候清理」。可选：

- **不自动化，靠人偶尔看一眼** `docker system df` —— 最简单，但「偶尔」的意思通常就是「想不起来」
- **服务器上挂一个 systemd timer，定期 `docker image prune -a`** —— 自动化；⚠️ 但 `-a` 会把**所有**未被容器引用的镜像删掉，
  而回滚要用的旧版本镜像正好属于这一类（回滚的真实落落在 ACR，本地删掉不影响回滚，只是下次回滚要重新拉）
- **保留最近 N 个版本、其余清理** —— 折中，但要写点脚本

**倾向第二档**，且把保留期设得宽一些（比如「未被引用超过 30 天才删」用 `--filter until=720h`）：
既不会天天手动，也不至于把刚发版的旧版本立刻清掉。等真出现磁盘告警再收紧。

## 本机遗留的两个 prod 容器（2026-10-03 新增）

上云之后本机只剩开发形态，但 `quizzy-server` 与 `quizzy-web` 两个容器**还留在本机 Docker 里**，
而它们都带 `restart: unless-stopped` —— **下次 Docker Desktop 一启动，它们就会自己回来**，
跑的还是不受任何 compose 文件管理的旧配置。不清理的话，「本机不再运行 prod」这件事只是名义上的。

清法一条命令（**保留 `quizzy-mysql`**，那是 dev 要用的）：

```bash
docker rm quizzy-server quizzy-web
```

**为什么还没做**：这一步需要先启本机的 Docker Desktop，而「启动 GUI 程序」这个动作**被本机安全策略拦了**
（AI 侧执行不了，提示也不要重试）。等主人在自己的终端里启一次，或明确说不用清。
