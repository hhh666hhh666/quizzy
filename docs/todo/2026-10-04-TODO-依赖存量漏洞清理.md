## ⚠️ 它们不会挡 CI——这是刻意的，别误以为「扫过了」

`deps` job 比的是 **PR 的增量**（base 与 head 两份快照的 diff）。
这 39 条是**存量**：base 与 head 上一样，进不了 diff，所以**永远不会让门禁变红**。

> ⇒ 这条门禁的语义是「**别再往里加新的**」，**不是**「仓库里现在是干净的」。
> 存量要另外管——这就是本 TODO 存在的理由。

### 还有 4 条 Maven 的 medium，**暂缓——因为它没法被验证**

`commons-compress` 1.26.0 · `commons-lang3` 3.18.0 · `log4j-api` 2.25.5 · `poi-ooxml` 5.4.0
（都是 easyexcel 带进来的传递依赖）。

⚠️ **其中两条是可达的**，不是理论风险：

- `commons-compress`：解压时的**死循环**与**解坏 Pack200 时 OOM**
- `poi-ooxml`：OOXML 文件的**输入校验**不当

而 **xlsx 上传是「公开注册后任何人都能用」的入口**（ADR 0017），所以攻击者能自己构造文件打过来。

**那为什么还暂缓？** 因为**没有任何测试会真的解析 Excel**：

- `QuestionImportServiceTest` 只测**导入校验**，不碰 xlsx 解析；
- 端到端 `07-import-export` 走的是 **JSON 粘贴**那一条路，不走 Excel；
- 于是「升上去 → CI 全绿」**证明不了 Excel 导入还活着**。

而 easyexcel 对 POI 版本**很敏感**（它深度包装 POI 内部结构），5.2.x → 5.4.0 不能假定安全。

⇒ 决定：**先补一条 Excel 烟测**（真的用 easyexcel 写一个小 xlsx 再导入回来），
有了它再升版本——那时 CI 红就代表真坏了。在那之前不动。

## 没定的事

**1 · 清不清、清到哪一档**（优先级：中）

多数是**构建期**依赖（`vite` / `postcss` / `esbuild` / `@babel/core`），不进生产产物，
暴露面与 `jjwt` 那类运行时依赖完全不同；`adm-zip` 在 `quizzy-mobile` 里，要单独看是不是运行时用。

可选：① 只清 high；② high + medium；③ 先只清**运行时**依赖，构建期那批等大版本升级时带走。

**倾向 ③**，理由：构建期依赖的漏洞要能被利用，前提是攻击者能让你构建不可信输入——
单人项目不成立；而把它们硬升上去反而可能弄坏构建链。

**2 · 存量怎么持续可见**（优先级：中）

现在只有「开 PR 时看增量」这一条，存量**没有任何自动化提醒**。
可选：① 靠 GitHub 的 Dependabot alerts 邮件（已开，0 成本，但只在**新公告**时通知）；
② 加一个每周定时跑的全量扫描 job（`dependency-review-action` 在非 PR 事件上用不了，
得换 Trivy 或 `npm audit`）；③ 不做，靠人偶尔去看一眼 Security 页。

**倾向 ① + 偶尔人眼**，暂不加定时 job（会重回「噪音门禁」的老路）。
