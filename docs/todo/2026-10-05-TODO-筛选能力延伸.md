# 待办：筛选能力延伸

创建：2026-10-05 · 状态：待办 · 优先级：低

这一份记的是「题库页筛选」这件事做完之后，自然浮出来的四处延伸。四条都**不影响本次交付的正确性**，
只是没做、并且值得记一笔，免得以后重新想一遍。

## 一、其它列表页的筛选状态还没写进网址（优先级：低）

**现状**：题库页已经把筛选条件放进 `route.query`（刷新与浏览器的前进后退都能原样恢复），
试卷、错题本、历史这三页仍然只把条件存在内存里，**一刷新就回到默认**。这几页各自都有分页或筛选控件，
所以「刷新丢状态」在它们身上同样成立，只是本次没人提。

**为什么现在定不下来**：本次只点了题库页，主人答的是「这次就做」；这三页要不要跟着铺开是另一个决定。
铺开要各自再写一遍「页面状态 ↔ 网址」的映射，是一次性的重复劳动，也可以等哪天真的嫌烦了再一起做。

**可选方案**：

- **A. 现在就一起铺开**——工作量约等于把题库页那段映射再写三遍；
- **B. 先不动，等某个页面真的让人难受了再单独做**（**倾向**）——一次只改一处，出了问题好定位，
  也避免在没有实际体感的时候替未来的自己拍板；
- **C. 先把那段映射抽成可复用的组合式函数再铺开**——前提是三页的控件形状确实一样，而这一点还没看过，
  贸然抽公共件大概率抽出个「谁都不太合用」的东西。

## 二、组卷的抽题规则没跟上「分类可多选 + 未分类」（优先级：低）

**现状**：题库页现在能按**多个**分类筛题、还能单看「未分类」的题；而抽题规则里的分类仍然是**单个**
`categoryId`。于是会出现「题库页筛得出这一批题，规则卷却表达不出同样的条件」这种不对称。

**为什么现在定不下来**：两条路都说得通——抽题规则的语义是「按条件现场抽题」，它天生偏向少而稳的几个条件；
而筛题的语义是「找题」，条件多是正常的。要不要对齐，取决于主人实际组卷时会不会想「只抽这两个分类」
或者「只抽没分类的题」。这个使用习惯目前**没有证据**。

**可选方案**：

- **A. 保持现状**，等真出现「想把某几个分类凑一张卷」的需求再说（**倾向**）——没有实际用例之前增加条件维度，
  只会把规则卷的面板做复杂；
- **B. 把规则的分类也改成多选 + 未分类**——⚠️ 这同样是**接口破坏性变更**，而且规则是以 JSON 存在
  `paper.rule_json` 里的，**历史卷里的 `categoryId` 是单个值**，读旧数据必须两条路都认，
  属于要单独发一版的改动。

## 三、「未分类」这个词被两处用得不一样（优先级：低，但**迟早会咬人**）

**现状**：两处同名、所指不同——

| 出处 | 「未分类」是什么意思 |
|------|--------------------|
| 界面与筛选（本次做的那个开关） | **这道题不属于任何分类**（没有分类） |
| 题库生成技能（`md-to-question-bank`） | 一个**真实的分类名**：源里推不出分类时，`category` 兜底成字符串 `"未分类"` |

于是存在一个会让主人困惑的组合：用那套技能导入一批题 → 那些题挂在**一个名叫「未分类」的分类**下；
回到题库页按「未分类」筛 → **一道都筛不出来**（它们是"有分类"的，只是名字叫这个）。

**2026-10-06 核实（流水线已跑过一轮）**：`question-bank/mysql/md/MySQL.md` 已出 189 题并整目录入库，
产物里 `category` **全部是学科名 `mysql`**——分类由「一个学科一个目录」的目录名提供，兜底**没被触发**；
而技能里那处兜底**仍然在**（只在分类推导不出来时才用到）。

**为什么现在定不下来**：触发条件是「源的分类推不出来」。按现在「一个学科一个目录」的调用方式它不会发生，
换成直接喂一个散装 md 就会。所以它不是已发生的问题，而是**一个还没被调用方式堵死的口子**。
好消息是：本次产物里没有这个分类，所以**改兜底名不需要重出已生成的产物**，成本比原先记的更低。

**可选方案**：

- **A. 把技能的兜底分类名改成别的**（比如「未归类」），顺手把 `CONTEXT.md` 里那句更正一并生效（**倾向**）——
  现在改不牵连已有产物，从源头上避免造出这个名字的分类；
- **B. 什么都不改**，只靠 `CONTEXT.md` 的说明兜着——零成本，但上面那个组合一旦发生，
  主人会先怀疑「筛选坏了」，排查成本高于现在改名的成本；
- **C. 让导入端把 `category: "未分类"` 特判成「没有分类」**——❌ **不推荐**：那是拿一个魔法字符串当语义，
  以后任何人写个正经名叫「未分类」的分类就会踩雷，而且这个特判藏在校验与入库之间，没人看得见。

## 四、列表接口没有「按 id 批量取题」（优先级：低）

**现状**：试卷编辑抽屉要回显「这张卷里都是哪些题」，手上只有一堆 `id`。而题目列表接口
（`GET /api/questions`）**没有 id 条件**，`size` 还被后端夹在 100；于是前端只能**按页翻找**，
直到找齐为止（`PaperEditDialog.vue` 的 `loadQuestions`，上限 50 页兜底）。

**为什么现在定不下来**：翻页方案是**对的**，只是笨——正常卷几页内就找齐，所以没有实际体感；
而加上这个条件要动 `QuestionQueryDTO` 与 `QuestionService` 的条件构建，是**接口能力**的扩张，
顺手做会把它混进「题集」那一轮（前端侧改动）里，两件事不该混在一笔里。

**可选方案**：

- **A. 给列表接口加一个 `ids` 条件**（条件构建可复用导出那条路径已有的 `in(id)` 写法）（**倾向**）——
  前端那句翻页循环随即退化成一个请求；
- **B. 保持翻页**——零改动，代价是引用了较早题目的卷要多发几次请求；
- **C. 把「按 id 取题」做成独立端点**——语义更明确，但多一个端点要维护、要测试，收益与 A 相同。
