创建：2026-10-01 · 状态：待办 · 优先级：中

## 邮箱验证码用哪个发信通道？

「公开注册 + 邮箱验证」这件事本身已经定在 [ADR 0017](../adr/0017-public-signup-service.md) 里，
并且**刻意推迟**到云上部署链路（备案、ACR、CI 自动部署、证书、备份、2C2G 调优）跑通之后单独做——
那条链路本身全是第一次，混着功能开发会让「到底哪一层坏了」难以判断。

现在挂着的是**发信通道**这一个点，因为用户已表达的偏好与它冲突：

| 已记录的偏好 | 与它冲突的地方 |
|---|---|
| 邮箱作为**登录名**，用户名降为昵称 | 收不到验证信 = 登不进来，发信通道从「辅助功能」升格为「登录的前置依赖」 |
| SMTP 用**现有个人邮箱** | 个人邮箱 SMTP 是最容易进垃圾箱、且有发信限额的通道；授权码泄露等于邮箱被冒用 |

**为什么现在定不下来**：两边各有一半道理——个人邮箱零成本、几分钟能通，适合先跑通；但它撑不住「登录依赖它」这个地位。
真实用户量和垃圾注册的实际规模都还是零，现在按负载选型是空谈。

**可选方案与倾向**：

- **阿里云邮件推送 DirectMail** —— 与 ECS 同厂商、大陆送达率好、按量计费极便宜。要求：发信域名已备案并配 SPF / DKIM。
  **倾向这个。** 一旦邮箱成为登录名，发信通道就该按「基础设施」而不是「临时通道」对待。
- **第三方（Resend / SMTP2GO / Brevo）** —— 接入简单、免费额度够个人用。代价是境外服务，大陆服务器访问可能慢或不稳，发往 QQ / 163 容易被判垃圾。
- **现有个人邮箱 SMTP** —— 零成本、几分钟能通。只适合当成「先跑通功能」的临时通道，不适合长期承载登录。

**做这件事时还要一起定的（现在都不定）**：

- 验证码存哪——[ADR 0002](../adr/0002-answer-progress-in-mysql.md) 定了不引 Redis，所以落 MySQL 新表
- 发码的限流维度（同一邮箱 / 同一 IP，双向都要）——不做就会变成别人免费的垃圾邮件发射器
- 未验证邮箱能不能登录，还是注册即拦住
- 顺带要不要加「找回密码」（邮箱登录之后这件事几乎顺手，但属新范围）
- 发码限流与 **注册风控**（图形验证码 + 按 IP 限流）是同一摊事，见 [`docs/todo/2026-10-03-TODO-注册风控.md`](./2026-10-03-TODO-注册风控.md)——两处不重复开清单
