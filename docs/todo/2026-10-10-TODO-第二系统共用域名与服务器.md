# 待办：第二个系统共用域名与服务器

创建：2026-10-10 · 状态：待办 · 优先级：中

## 另一套系统要不要、以及怎么共用 quizzy 现在的域名与那台阿里云服务器

**为什么现在定不下来**：这取决于三件只有主人知道的事——第二个系统的**技术形态**（决定内存开销）、它能接受的**访问形式**（子域名 / 子路径）、以及愿不愿意**给服务器升配**。荧能定的部分（入口怎么接、隔离怎么保证）已经有明确倾向，但不该替主人拍这些。

**现状（有据，出处在文件里）**

- 服务器是阿里云轻量 **2C2G**；`docker-compose.prod.yml` 的注释里写着这台机**实测可用内存只有约 800MB**，MySQL 已占约 480MB、JVM 拿 384MB，余量接近零；加上宝塔本身还要吃两三百 MB。
  ⚠️ **本行三个数字已于 2026-10-10 实测刷新**（available 602MB / MySQL 533MB / swap 已用 197MB）——完整分布与修正见文末「三次追加」一节，请以那一节为准。
- 对外入口由**宿主 nginx（宝塔）**独占 80/443，反代到 web 容器的 `127.0.0.1:8081`；新系统只能照抄这个形态绑别的回环端口。
- 域名已 **ICP 备案通过**，宝塔签 Let's Encrypt 证书、开了强制 HTTPS（80 → 301）。

**可选方案（倾向已写）**

| 方案 | 做法 | 倾向 |
|------|------|------|
| **二级子域名**（`系统B.主域名`） | DNS 加一条 A 记录 → 宝塔新建站点 + 自有证书 + 反代到新回环端口 | ✅ **推荐**。浏览器按「协议+域名+端口」隔离，**不按路径**，所以子域名能与 quizzy 天然隔离；子路径做不到这点 |
| 子路径（`主域名/系统B/`） | 同一站点加 `location` 反代 | ❌ 不推荐。与 quizzy **同 origin**，localStorage / cookie 完全共享，两家的 `*_token` 会互覆盖（表现为莫名掉登录）；还要改新前端的 `base` 与路由 history 前缀 |
| 独立域名 | 另购域名、另行备案 | 除非那个域名已备案，否则走一遍 ICP 备案（约 1–3 周），不划算 |

**必须先回答的前置约束**

- **内存**：再上一个 Java/Spring Boot 服务，2C2G 必爆（MySQL 480 + 两套 JVM）。要么新系统够轻（静态站 / Node / Python 小服务），要么先把服务器升到 2C4G、并按 `docker-compose.prod.yml` 的注释重新分配 MySQL buffer pool 与 `-Xmx`。
- **数据库**：倾向**共用 quizzy-mysql 但另建 database + 专用账号**（不再起第二个 MySQL 容器；用 root 或共用 quizzy 库等于把两个系统的 blast radius 焊死在一起）。
- **备案口径**：已备案主域名下的二级子域名，通常不需要重新 ICP 备案——**这条是推断，动手前须在阿里云备案控制台核实**（各省管局口径有差异）。

**动手后要同步的文档**：`docs/operations/deployment.md`、`deploy/nginx/`（加一份第二个站点的对照模板）、`docs/design/数据模型.md`（若共用数据库实例）。

## 2026-10-10 追加：主人已做的三项选择，与其中暴露的冲突

| 事项 | 主人的选择 |
|------|-----------|
| 第二个系统形态 | **Java / Spring Boot** |
| 共用方式 | **二级子域名**（DNS 加 A 记录 + 宝塔新建站点 + 独立证书） |
| 服务器资源 | **不动硬件（维持 2C2G），靠严格限内存硬塞** |

⚠️ **前两项组合没有冲突，第三项与前两项直接打架。** Spring Boot 的最小实用足迹约 300–400MB RSS（堆只是其中一部分，还要算元空间、CodeCache、线程栈、直接内存、JVM 自身）；在「可用内存约 800MB、MySQL 已占约 480MB、quizzy 的 JVM 已拿 384MB」的家底上再加一个，**总量必然超预算**，触发 OOM-killer。

**未解决，需要再拍一次**（荧的倾向写在前）：

1. ✅ **加 4GB swap**（倾向这个）—— 唯一能在不动硬件的前提下让两台 JVM「活着」的手段。代价是高峰期换页卡顿，且阿里云轻量的盘 IO 有限；它不是解决问题，是把「进程被杀」换成「慢」。
2. 把 quizzy 的 MySQL buffer pool 压到 64M、`-Xmx` 压到 256m，新系统压到 `-Xmx224m -Xss512k -XX:TieredStopAtLevel=1` —— 能省出 100–200MB，但**不足以抵消一个 JVM 的入场费**，只能作为 1 的配套。
3. 升配到 2C4G —— 主人当前已排除，但这是唯一真正解决问题的选项（阿里云轻量升配差价需查控制台确认）。
4. 新系统改成「按需启停」（低频使用时才起）—— 只适合访问量极小的场景。

**不管最后选哪条，都要先做且不作为可选项的一步**：SSH 上去跑 `free -m`、`df -h`、`docker stats --no-stream`，用**实测值**替换本文件里引用的仓库记录值（后者是发版时记的，可能已漂）。没有实测值，上面所有估算都只是估算。

## 2026-10-10 二次追加：内存方案已定（只压 JVM，不加 swap）+ 止损线

> ⚠️ **本节结论已被「三次追加」的实测数据推翻**（缺口估算、MySQL 估算、止损线数字三项均作废）。保留原文只为存档当时的推理，**请勿据此做决策**，看文末的三次追加。

主人最终口径：**不动 2C2G 硬件、不加 swap，靠极限压缩 JVM 与 MySQL 参数硬塞第二套 Spring Boot。**
数据库：**共用 quizzy-mysql 实例，另建 database + 专用账号**（不共用 quizzy 库、不用 root）。

⚠️ 性质说明（写清楚，免得以后当成「已解决」）：**这是带风险的试跑，不是解决方案。** 压到极限后账面仍差约 100MB，
一旦真耗尽，OOM-killer 会挑最大进程杀——通常是 quizzy-server 或 mysql，**mysql 被强杀有数据损坏风险**。

### 可抄的参数（改 `docker-compose.prod.yml`，不是改 `.env`）

| 服务 | 现参数 | 压后 | 为什么能省 |
|---|---|---|---|
| mysql | `--innodb-buffer-pool-size=128M` `--max-connections=50` | `=64M` / `=30` + `--performance_schema=OFF` + `--table-open-cache=64` | ⚠️ **2026-10-10 实测刷新：`performance_schema` 一项就吃 235MB**（不是「几十 MB」），在 MySQL 容器 533MB 里占 44%；关掉它是全服务器性价比最高的一刀 |
| quizzy server | `-Xms128m -Xmx384m -XX:MaxMetaspaceSize=128m -XX:MaxDirectMemorySize=48m -XX:+UseSerialGC` | `-Xms192m -Xmx256m -XX:MaxMetaspaceSize=96m -XX:MaxDirectMemorySize=32m -XX:ReservedCodeCacheSize=48m -Xss512k -XX:TieredStopAtLevel=1 -XX:+UseSerialGC` | **最大一笔省在线程栈**：Tomcat 默认 200 线程 × 1MB = 200MB；`-Xss512k` + `max-threads=32` 后只剩 16MB |
| 第二套 | — | 同上口径，`-Xmx224m` | 同理 |

配套：第二套 compose 的 `name:` **必须改掉**（quizzy 是写死的 `name: quizzy`，同名会被并进同一个 compose 项目）；
端口绑另一个回环（如 `127.0.0.1:8082:80`）；**任何时候都不要对 quizzy 项目执行 `down`**。

### 止损线（触发即停，必须回头二选一：加 swap 或升配）

1. `docker stats --no-stream` 里**四个容器 RSS 合计 > 750MB**
2. `dmesg -T | grep -i -E 'killed process|oom'` **出现过任何一次**
3. quizzy 的 `/api` 出现 5xx 或健康检查从 healthy 掉出，且日志里是进程被杀（不是业务异常）

### 待补（给了才能开工）

- 第二个系统的名字（决定子域名、compose 项目名、镜像名）
- 想用的回环端口（默认 8082）
- 数据库名与账号名
- 它要不要共用 quizzy 的**账号体系**（不共用则简单；共用则涉及 JWT secret 与跨域，是另一个话题）

### 第二套的资源口径（2026-10-10 按实测定，可直接抄）

- **`-Xmx192m`**（理论上限约 434MB = 192 + 固定附加 242MB），固定附加照抄 quizzy 口径：
  `-XX:MaxMetaspaceSize=112m -XX:MaxDirectMemorySize=32m -XX:ReservedCodeCacheSize=48m -Xss512k -XX:TieredStopAtLevel=1 -XX:+UseSerialGC`
- 另加 `SERVER_TOMCAT_THREADS_MAX=32` 与 `mem_limit: 480m`（内核级兜底）
- **推导**：整机 available 1011MB，扣掉「quizzy 吃满后的增量 291MB」、扣掉「MySQL 因第二套接入的预留 100MB」、
  再扣「安全垫 175MB」→ 净预算约 445MB；`192 + 242 = 434 ≤ 445` ✓。
  完整模型见 `docs/operations/内存策略.md` 第四节的容量规划公式
- ⚠️ **上线时错开部署窗口**：两个 Spring Boot 同时重启（启动期堆需求高于稳态）是真正的危险时刻，别和 quizzy 的 `up -d` 撞车

### ⭐ MySQL 那 533MB 的内部拆解（本次最有价值的发现）

| 分组 | 占用 |
|---|---|

参数现状：`innodb_buffer_pool_size`=128M ✓ 生效、`innodb_log_buffer_size`=**64M**（默认值，对小实例偏大）、`table_open_cache`=**4000**（默认值，偏大）、`performance_schema`=**ON**。

### 修正后的结论（⚠️ 推翻「二次追加」里的判断）

**原先说的「缺口 300~450MB、必爆」是错的。** 按实测重算：

1. **MySQL 有三刀可切，合计约省 280~310MB**：关 `performance_schema`（**235MB**）、`innodb_log_buffer_size` 64M→16M（约 48MB）、`table_open_cache` 4000→400（数十 MB）
2. 切完之后 available 从 602MB 升到约 **880MB**
3. 再放第二套 Spring Boot（**按上限 450MB 预算**）→ 仍有约 **430MB** 安全垫

⇒ **不动硬件、不加 swap，可行；而且不必走「合并成一个 JVM」那条路。**
「只用一台 JVM」作为备选保留（若日后内存再吃紧可重提），但它的四个代价——发布绑死、故障域连坐（堆 OOM 时 `restart` 策略救不了）、依赖版本锁死、双数据源配置——在实测数据面前不值得付。

### 新的止损线（按实测校准，替换「二次追加」里的旧值）

1. `docker stats --no-stream` 容器 RSS 合计 > **1100MB**（当前三容器 804MB + 第二套预算 450MB 的合理上限）
2. `free -m` 的 **swap 已用 > 500MB**（当前 197MB）
3. `dmesg -T | grep -i oom` 出现任何一次
