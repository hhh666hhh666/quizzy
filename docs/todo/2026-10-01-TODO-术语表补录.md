# 待办：术语表补录

创建：2026-10-01 · 状态：已解决 · 优先级：低

## 结论：三条都不补，并把现存的「版本号」条目瘦身

**2026-10-01 18:56 结案**，跑了一轮 `domain-modeling`（过程见
[决策日志](../decisions/records-and-glossary.md)的第 2 节）。

原倾向是「只补『镜像 tag』一条」，**读完 `CONTEXT-FORMAT.md` 的收录规则后自己把它否掉了**。
`CONTEXT.md` 第 3 行写着「刻意不含存储与实现细节」，格式规则则要求「只收本上下文独有的概念」，
三条候选逐一对：

| 候选说法 | 判定 | 理由 |
|---|---|---|
| 镜像 tag | ❌ 不收 | 是 Docker 的概念，不是本项目的领域概念；且 `CHANGELOG.md` 开头那张表**已经定义了它**，再写一遍就是第二份会漂移的定义（ADR 0006） |
| 构建期注入 | ❌ 不收 | 是手段，不是概念；典型实现细节 |
| 领先信息（副行） | ❌ 不收 | UI 部件名，描述的是 `HEAD` 与 tag 的关系 |

**反向查出一条真问题**：现存的「版本号」条目是全表 **28 条里唯一**点名 `git tag` / `pom.xml` /
`package.json` / compose 的，与「不含实现细节」自相矛盾，且那半段与 `CHANGELOG.md` 的开头表格
逐字重复。已改成：条目只留「是什么」，机制以一行指路交给 `CHANGELOG.md` 与 ADR 0015。

**顺带定下一条写法约束**：`CONTEXT.md` 的条目定义里**不出现文件名、工具名与命令**——
机制一律用「去哪看」的指路行交给 owner 文档。

## 当时的判断（已被上述结论推翻，保留备查）

**现状**：2026-10-01 的「关于」功能 + 版本号治理那轮 grill 定下了几个新说法，当时散在两处——
「版本号」已进 `CONTEXT.md`，「镜像 tag」/「构建期注入」/「领先信息（副行）」只在
`docs/decisions/version-and-about-feature.md` 里；而「镜像 tag」这个词已在 `CHANGELOG.md`
与 `docs/operations/deployment.md` 里被正式使用。

**当时为什么定不下来**：术语表归 `domain-modeling` 管，补录要跑一遍那个流程；而且这几条里至少两条
是实现细节的名词，未必够格进术语表。当时给的三个方案与倾向：

- **A. 只补「镜像 tag」（当时倾向）**——它会被反复使用，`_Avoid_` 能写得很实。
- **B. 三条全补**——术语表更全，但会引入非领域词。
- **C. 都不补**——保持只收领域概念，代价是「镜像 tag」继续在别的文档里裸用。

结论选的是 **C 的加强版**：都不补，且顺手把已越界的那条拉回正轨。
