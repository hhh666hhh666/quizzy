# 待办：Release 对象漏建（tag 推了，Release 没建）

创建：2026-10-14 · 状态：待办 · 优先级：中

## 背景

为什么会有这条：v1.9.0 发布时发现 **v1.7.0～v1.8.3 五个版本只推了 tag、从没建过 Release 对象**
（`/releases` 页上 Latest 一度还停在 v1.6.0）。这不是第一次——2026-10-06 已经补建过一次
（v1.2.0～v1.5.0）。CHANGELOG 的维护约定里原话是「忘了建不会有任何人提醒，只能靠这条约定兜着」，
而这个约定已经兜漏了两次。

当日已手工补齐五个（正文取自 CHANGELOG 对应版本段，段内相对链接改写成指向各 tag 的绝对地址），
并把被误抢的 Latest 指针从 v1.8.0 拨回了 v1.9.0。本 TODO 管的是「下次别再漏」。

## 可选方案

- **方案甲**：CI 加一个对账 job——`git tag` 列出的 `v*` 与 `gh release list` 对差，缺一个就红
  —— 代价：workflow 加十几行；要处理「Release 晚于 tag 建」的时序（tag 自己的 push 事件只查它自己，
  其余 tag 放到 push master 或定时事件里查）。
- **方案乙**：维持人工约定，靠发版时人多看一眼 —— 代价：已经兜漏两次，零成本也零效果。
- **方案丙**：把建 Release 并进 `release.yml`（推 tag 自动建，正文取 CHANGELOG 段）
  —— 代价：违背「刻意不把建 Release 做成自动化」的既有结论（正文是给人看的说明书，要人过目），
  且「相对链接改写成绝对地址」这一步没法可靠自动化。

➡️ 倾向：方案甲。它不动「正文人工写、人工过目」这条结论，只补上「漏没漏」这个**可机械验**的部分——
与 `check-version.sh` / `check-doc-links.sh` / `check-todo-archive.sh` 同一个模式（纪律的三件套：
规则让人知道、`/wrap-up` 让人记得做、脚本让人不做就过不去）。丙否掉的理由同 CHANGELOG 维护约定原话。
