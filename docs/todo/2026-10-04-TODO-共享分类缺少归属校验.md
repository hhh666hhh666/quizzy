# 待办 · 共享分类缺少归属校验（任意登录用户可删掉全体共用的分类）

**发现时间**：2026-10-04 · **发现者**：荧（补服务集成层用例时）· **状态**：待主人决定

## 现象

`docs/context` 与 `CONTEXT.md` 都写着分类是「所有人共用同一套」，代码也确实如此：

- `Category` 实体只有 `id / name / sort / createTime`，**没有 ownerId** —— 共享是设计，这点没问题；
- 但整个分类模块（`CategoryService` / `CategoryController`）**没有任何归属校验**：
  `create` / `rename` / `delete` 都不校验「谁在动它」；
- 而 `delete` 不只是删一条配置：`CategoryService#delete` 会先 `questionMapper.clearCategory(id)`
  ——把**所有用户**挂在这个分类下的题目的分类引用一起清空，然后才删掉分类本身。

## 为什么它是风险

按 [ADR 0017](../adr/0017-public-signup-service.md) 服务已经**对公网开放、任何人注册即可用**。于是：

> 任何一个注册用户，都能删掉全体共用的分类，并让所有人的相关题目一次性失去分类归属。

这是**跨用户的、不可逆的副作用**，而且没有确认步骤、没有审计、也没有回收站。
与个人工具时期（只有主人一个用户）相比，风险性质变了。

## 荧的判断

- **共享本身不用改**——分类就是共用的，这与 [ADR 0003](../adr/0003-public-questions-by-empty-owner.md)
  的「公开题」理念一致，加 ownerId 反而会把共享数据切碎。
- **该收敛的是「删除」这个动作**：创建与改名影响面小，删除是唯一的破坏性操作。

## 可选方案（需要主人拍板）

| 方案 | 做法 | 代价 |
|------|------|------|
| A · 保持现状 | 不动，接受风险 | 公开服务下等于把共享数据交给任意注册者 |
| B · 记录创建者，只允许创建者删 | 给 `Category` 加 `createdBy` 字段，删除时校验 | 要迁移；共享语义不变，只是删除受限 |
| C · 删除改为「解绑」 | 保留分类记录，只清引用；或加回收站 | 语义最安全，但要改接口与前端 |
| D · 收敛到管理员 | 引入角色/管理员概念 | 改动最大，与「个人工具」定位有张力 |

荧倾向 **B**：改动小、与共享语义不冲突、能挡住最坏情况；
若觉得 B 仍不够，再考虑 C。
