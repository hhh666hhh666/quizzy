# 待办：前端视觉重构

创建：2026-10-07 · 状态：待办 · 优先级：中

> 关联决策见 [ADR 0031](../adr/0031-pc-frontend-rebuild-shadcn-vue.md)。本文件只收**这次重构留下的未定项**；重构本身的执行顺序不在这里（那是会话过程，见 `docs/worklog/`）。

## 1. 中文字体：要不要自托管子集

**现状**：重建时先用**系统字体栈打底**，字体在 token 层留出变量位（一个 `--font-family` 与一套字阶）。
**为什么现在定不下来**：自托管中文子集要选字、切子集、管许可、防 FOIT，成本明显；而「精美」的收益主要来自排版尺度 / 间距 / 颜色，字体是锦上添花且可后补。
**可选方案**：**A 先不动**，等浅色版整体成型后回看效果再决定（**倾向**）；B 现在就上（如思源黑体子集）——除非明确觉得系统栈不好看，否则不值得提前付这个成本。

## 2. 文档组织：出现「文档打架」时再看情况重构

**现状**：按 ADR 0031，仓库根会有 `PRODUCT.md`（受众 / 目标 / 品牌承诺）与 `DESIGN.md`（视觉系统，派生快照）；它们的部分内容与 [`scope.md`](../requirements/scope.md) **已知重叠**，**冲突时以 `scope.md` 为准**。`docs/design/` 的目录组织也维持原样。
**为什么现在定不下来**：重叠是**知情的取舍**（换"就地划清"要多轮对齐，收益不及成本）；真正该动手的信号是**出现实际冲突**，而不是预设一次目录重组。
**触发条件**：**当同类内容在两处对不上、且已经影响到实际判断时**，回来考虑重构文档组织（含 `docs/design/` 与根 `PRODUCT.md`/`DESIGN.md` 的分工）。
**可选方案**：A 到那时再定（**倾向**）；B 现在就把边界划死（`PRODUCT.md` 只管受众 / 语气 / 视觉约束，`scope.md` 只管功能范围与不做，两处互指）——若第 1 次真撞上，就走 B。

## 3. 「组件测试暂缓」的理由在重构后会失效

**现状**：[`docs/testing/系统说明.md`](../testing/系统说明.md) 记着「组件测试（Vitest 之类）与 lint 本轮暂缓」，理由之一是**无共享组件库**（Element Plus / wot-design-uni 已兜底大部分交互）。
**为什么现在定不下来**：shadcn-vue 的组件**源码进仓库**后，「无共享组件库」这条理由**不再成立**——但要不要真补组件测试，取决于重建后自研组件的实际体量。
**触发条件**：PC 前端重建**落地后**回来重评。
**可选方案**：A 落地后按实际情况再定（**倾向**）；B 现在就把它列成必做——但**先别**，理由尚未被现实检验。

## 4. 视觉口味落地：色板、主色色相、登录页形态（2026-10-08）

> ⚠️ **口径已变更**：曾经有一轮 Stitch 对照图是按**旧口径**（「冷中性底 / 留白宽松 / **只有一个强调色** / 柔影层次」）出的。
> 主人在 **10:19 改口**为「**L3 大面积彩色面**」并定了「**正文那一块留近白**」，**11:15** 又加了
> 「**玻璃只给浮层用**」的两层语言。新口径已落进 `quizzy-web/src/styles/tokens.css`。
> **那轮旧图只可参考、不能当准**；下面几条都按**新口径**重新表述。

### 4.1 色板要不要升级成 Material 的「色调容器」系统

**现状**：token v2 里的「受控色板」是**荧手写的 5 个 tint**（`--color-tint-{blue,cyan,violet,green,amber}`）。
**为什么现在定不下来**：主人先后挑中的两张参照（Material You、玻璃拟态）**指向同一个做法**——背景用**主色派生出的浅色"亲戚"**
（Material 叫 **tonal container**：`primary` → `primary-container` → `surface`，越往下越淡、面积越大）。
那套是"**给一颗种子色、自动算出整套协调色调**"的算法：**比手写色值更系统，而且深浅两档天生成对**；
代价是它的浅色容器**常被批对比度不足**，要用就得**配工具算对比度**（不能凭眼睛）。
**可选方案**：**A 换成"由主色派生色调组"的思路**（**倾向**）——一劳永逸，深浅一起解决；
B 保留手写的 5 个 tint（够用，但以后每加一个色都要手调、深浅还各来一遍）；C 先看新口径的出图再定。

### 4.2 对错与状态的配色怎么定

> 原本这条问的是「**要不要放弃绿红**」——那个前提来自**旧口径的"单强调色"**，**已经失效**
> （L3 本来就允许多种颜色）。真问题变了。

**现状**：`QuizResultView.vue` 现在用 Element Plus 的 `success` / `danger`（绿 / 红）给选项与状态标签上底色；
token 里已有语义色 `--color-ok` / `--color-warn` / `--color-danger`。
**为什么现在定不下来**：**色值**还没定（要不要比 EP 的柔和些），而且**颜色不能是唯一通道**——
色盲用户与"减少透明度/高对比"模式下都得读得出来。
**可选方案**：**A 沿用语义色，但强制补非颜色通道**（对错同时有文字 / 图标 / 位置线索）（**倾向**）；
B 只保留红（错）、正确不上色——省一个色，但"正确"少了即时确认感。

### 4.3 主色（强调色）的色相

**现状**：三个候选并存——token v2 里是荧暂定的 `oklch(55% 0.18 262)`（**蓝**）；
Stitch 那轮自己推出了 `#2B59C3`（**钴蓝**）；主人随后给的 **Material 参照用的是 `#6750A4`（紫）**。
**为什么现在定不下来**：色相**要在整屏铺开的浅色版上才判断得准**（单看一个色块会误判）。
**可选方案**：**A 开一组对照：把三个色相各铺一版再看**（**倾向**）；B 就用现在的蓝往下推（省一轮，但等于替主人做了决定）。

### 4.4 登录页是双 tab 还是独立卡

**现状**：线上 `LoginView.vue` 是「登录 / 注册」两个 tab 挤在同一张卡里；那轮三版都画成了**独立登录卡 + 「还没有账号？注册」链接**。
**为什么现在定不下来**：这是**产品决定不是视觉决定**——tab 形态让「注册」与「登录」同等可见（配合「公开注册、开箱即有题可刷」），链接形态则更干净。
**可选方案**：**A 保持现状双 tab**（**倾向**）——新用户注册是主线路径之一，不该被降成一行小字；B 拆成独立登录卡 + 注册链接（更贴口味，但要单独做注册页）；C 拆成两个独立路由页面（最重）。
