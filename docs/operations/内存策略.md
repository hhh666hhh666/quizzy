# 内存策略

这台服务器（阿里云轻量 **2C2G**，可见内存 1870MB）是全项目最硬的资源约束。本文回答三件事：
**内存花在哪**、**每个服务为什么配成这样**、**什么时候该动手调整**。

> **参数值的真相源是 [docker-compose.prod.yml](../../docker-compose.prod.yml)**（MySQL 的 `command:` 段、
> 后端的 `JAVA_TOOL_OPTIONS`、三个服务的 `mem_limit`）。本文只写**为什么这么定**与**怎么算出来的**；
> 若本文的数值与 compose 不一致，以 compose 为准并顺手把本文改对。

## 一、内存都花在哪儿了（2026-10-10 实测基线）

采集命令：`free -m`、`docker stats --no-stream`、`ps aux --sort=-rss`、`swapon --show`

| 占用方 | 实测 | 备注 |
|---|---|---|
| quizzy-mysql | 161 MB | 关掉 `performance_schema` 之后 |
| quizzy-server | 207 MB | `-Xmx256m` 的低负载读数 |
| quizzy-web | 4 MB | nginx + 静态文件 |
| 主机侧 | 约 390 MB | 宝塔三件套 156 / Docker 栈 138 / 云盾 41 / 宿主 nginx 29 / 其余 26 |
| 内核与不可回收 | 约 97 MB | |
| **整机 available** | **1011 MB** | used 859MB；另有 1GB swap（其中 194MB 是历史冷页） |

⚠️ **「主机侧约 390MB」是这台机器上最大的一块不可控开销**，其中宝塔（面板 + 任务 + site_total）独占 156MB。
它是既有取舍而非浪费——宝塔在管 443 的证书与反代；换自建 nginx 能省一百多 MB，但会丢掉证书自动续期。

## 二、三个服务各自的策略

### MySQL：省在这里最划算

2026-10-10 的实测把 MySQL 从 533MB 压到 161MB，其中**单项最大的是 `performance_schema`（235MB，占当时容器内存 44%）**。
三条措施连同代价都写在 compose 的注释里，这里只留判据：

- **关 `performance_schema` 不影响任何业务功能**，代价是失去它的性能诊断视图；以后要做 SQL 级性能分析时临时开回来。
- `innodb_log_buffer_size`（原 64M）与 `table_open_cache`（原 4000）都曾被默认值顶高，按「自用工具」的实际负载配。
- **`innodb_buffer_pool_size` 2026-10-16 由 128M 降到 64M**（同时把 `innodb_buffer_pool_chunk_size` 降到 32M）：
  原判据「压它是亏本买卖」成立于**只有 quizzy 一个系统**、容器驻留 161MB 的时候。fit-app 接进来之后驻留涨到
  315MB / 硬顶 384MB，并已被内核 OOM-killer 杀掉**三次**——推力是餐照：把数 MB 的 `MEDIUMBLOB` 写进
  `meal_photo` 时，InnoDB 要在缓冲池**之外**再分配行缓冲，正好顶在这块天花板上。**在 384MB 的硬顶下，
  128M 的缓冲池已经买不起**，性能与「不被杀」之间只能选后者；自用工具数据量小、热点页少，64M 够用。
  ⚠️ 降 pool 必须**同时**降 chunk size：缓冲池不能小于一个 chunk，而 chunk 只能在启动时设；只改 pool
  会被 MySQL 启动时向上取整回 128M（在线 `SET GLOBAL` 同样被 Warning 1210 拒绝）。
- **`swappiness=0` 让匿名页没有退路（2026-10-19 补）**：宿主与容器当时都是 0，内核不会把匿名页换出。
  2026-10-19 18:31 的 OOM 现场：cgroup `anon 383.6MB` 顶满 `384MB`、`file` 仅 0.4MB、容器 swap 占用 **0**，
  尽管宿主还有 753MB 空闲 swap——**没有任何可回收的东西，只能杀进程**。现在容器显式 `mem_swappiness: 60`。
- **`temptable_max_ram` 默认 1GB，比 384MB 硬顶还大（2026-10-19 补）**：内部临时表（TempTable 引擎）
  在内存里最多可吃到 1GB，等于没有上限；一次大 GROUP BY／排序就能把它顶穿。现在钉到 **64M**，超出落盘。

### Spring Boot：堆只是其中一半

**这是本文最该记住的一条**：`-Xmx` 不是「这个进程最多占多少」，它只是**堆**的上限。
一个 Spring Boot 进程的**理论上限**是：

```
理论上限 ≈ -Xmx + 242MB（固定附加）
固定附加 242MB = 元空间 112 + 直接内存 32 + 代码缓存 48 + 线程栈 ~15 + JVM 自身 ~35
```

所以 quizzy-server 配 `-Xmx256m` 时，**理论上限约 498MB**——做容量规划要按这个数，不是按 256MB。
（现实高水位约 420MB，因为各项不会同时吃满；但规划该用前者。）

已经压过的五处（都在 `JAVA_TOOL_OPTIONS` / `SERVER_TOMCAT_THREADS_MAX`，理由见 compose 注释）：
`-Xss512k`、`-XX:TieredStopAtLevel=1`（只用 C1，省掉 C2 编译线程与大部分代码缓存）、
`-XX:ReservedCodeCacheSize=48m`、`MaxDirectMemorySize=32m`、Tomcat 工作线程封顶 32。

⚠️ **已进入收益递减区**：再压只剩两条路——`-Xmx` 继续降（约 30MB，但吃掉 Excel 导出/批量导入的峰值余量），
或上 AppCDS 类共享归档（元空间 20~40MB，但要改 Dockerfile 重建镜像）。**除非实测出问题，否则别继续压。**

### web（nginx）：可以忽略

4MB，不用管。

## 三、内核级硬顶：`mem_limit`

JVM 与 MySQL 的参数只能约束「它们自己认识的内存」。真出现参数管不住的泄漏时，
`mem_limit` 让内核 **OOM-kill 掉单个容器**，而不是拖垮整机。

三个服务的取值逻辑一致：**实测占用的 1.3~2.4 倍**。这是保险，不是配额——设太紧反而增加误杀风险。

## 四、要加一套新系统时怎么算

```
可给新系统的预算 = 当前 available
                 − 已有服务的增量（若新系统共用这台 MySQL，要给它预留 ~100MB：
                    连接数上升 + 数据量增长都会让它的驻留往上走）
                 − 安全垫 175MB（防止整机贴到 swap 而触发换页甚至 OOM）
```

新系统自身的参数照抄 §二 的同口径，并满足：

```
新系统的 -Xmx + 242MB ≤ 上面算出来的预算
```

⇒ 这台机上的落地口径是 `-Xmx192m`（理论上限约 434MB）。
**具体的第二套系统规划属于未决事项，见 [docs/todo/](../todo/)，不在本文排队。**

## 五、止损线（触发就该动手，别硬扛）

1. `docker stats --no-stream` 里任一容器的占用逼近它的 `mem_limit`
2. `free -m` 的 **swap 已用持续上涨**（当前 194MB 是历史冷页，不涨就不用管）
3. `dmesg -T | grep -i oom` 出现任何一次

⚠️ **swap 有占用不等于出事**：冷页待在 swap 里反而把物理内存让给热数据，判断标准是它**涨不涨**。
同理，用 `swapoff` 把冷页读回内存是反向操作，**别做**。

## 六、日常观察命令

```bash
free -m                                                                  # 整机与 swap
docker stats --no-stream                                                 # 各容器占用与 mem_limit
docker exec quizzy-server cat /proc/1/status | grep -E 'VmRSS|Threads'   # JVM 真实驻留与线程数
```

⚠️ 后端镜像只有 JRE（没有 `jcmd`/`jstack`），所以 JVM 的构成只能从 `/proc` 反推——上面第三条就是那个入口。
排障的其余入口在 [runbook.md](./runbook.md)。
