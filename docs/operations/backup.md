# 备份与恢复

## 现状一句话

导出脚本已写好并实测跑通，但**没有挂到任何调度上**；备份默认落在项目内，与 MySQL 数据在同一个盘——**这是「复制」不是「备份」**。

完整的风险分析与盘位（哪个盘还有空间）见 [docs/todo/2026-09-20-TODO-数据库备份.md](../todo/2026-09-20-TODO-数据库备份.md)，本文不复述。

一句背景，决定了这份文档的优先级：**题库是这项目唯一的资产——容器可以重建，题不能。**

## 手动跑一次

用法、备份位置、保留策略都写在 [scripts/backup-mysql.sh](../../scripts/backup-mysql.sh) 的头部注释里——那儿是真相源，脚本改了文档不用跟着改。

脚本没说、但值得知道的是**什么时候该手动跑一次**：

- 改动数据库结构之前（改已执行的 Flyway 迁移、手工改表）；
- 升级或大改之前；
- 很久没跑过、而调度又还没挂上的时候。

## 保留策略

保留多久由 `.env` 的保留天数变量控制（见 [.env.example](../../.env.example)），过期文件由脚本自己清理。**本文不写具体天数**——那是一个会变的默认值。

## 恢复（⚠️ 尚未演练）

**本仓库目前没有任何恢复脚本，下面也没有经过实际演练的步骤。** 备份文件存在不等于能恢复——唯一可信的验证是真恢复一次。

思路（**首次务必在临时库上验证，不要第一次就对着正经库跑**）：

1. 确认要恢复的备份文件存在且非空（脚本本身就有非空校验，空文件会被判失败并删掉）。
2. 在一个**临时库**里导入，确认表与数据都在。
3. 确认无误后再动正经库，且动之前先对当前状态再跑一次备份。

具体命令待演练后补进本文档，或补成 `scripts/restore-mysql.sh`——**演练一次恢复**是下一批文档工作的第一个动作。

## 怎么判断备份是好的

- 脚本层面的校验：导出文件非空，否则判失败（见脚本）。
- 真正的校验：恢复一次。「非空」只能证明导出过程没报错，**不能证明能恢复**。
