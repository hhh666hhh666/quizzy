# 测试系统说明

**目的**：讲清 quizzy 的测试系统**为什么**是现在这个形状——分几层、每层回答什么别层回答不了的问题、能保证什么、**明确不保证什么**，以及加新功能时该补哪层测试。

**读者**：改代码前想知道「安全网在哪、这次要补什么」的人。

**真相源**：本文档是**设计意图**的真相源。**现状与清单**（有哪些测试类、CI 跑哪些 job）在 [README](./README.md) 与 `.github/workflows/`，本文档**不复制**。规则数值（掌握阈值、字段名、响应信封形状）一律指向代码，也不复制。

---

## 一句话

**三层，每层存在的理由是「它有一个别层问不出的问题」。**

层数不是越多越好——加一层必须能说出「它独有的问题是什么」，说不出来就不该加。反过来，能被别层覆盖的也不该重复测：**同一件事只在一层验，避免两处断言互相漂**。

## 分层总表

| 层 | 回答什么问题 | 靠什么跑 | 需要机器上有什么 | 跑在哪 |
|----|--------------|----------|------------------|--------|
| **单元** | 单个类的逻辑对不对 | JUnit 5 | 无 | 任意机器 |
| **接口**（第二层的一种形态） | HTTP 契约、鉴权、**数据边界**对不对 | 真 Spring + 真 MySQL | Docker | CI / 本机（可选） |
| **服务集成**（第二层的另一种形态） | 跨组件协作、事务、**多表状态一致** | 真 Spring + 真 MySQL | Docker | CI / 本机（可选） |
| **端到端** | 用户在浏览器里走一遍对不对 | 真浏览器（Playwright） | Docker + 浏览器 | **只在 CI 的一次性环境** |

第二层的两种形态**不是两个层**，是同一层的两种切入方式，区别只在「从哪里进去」：

- **接口形态**：从 HTTP 进去。问的是**约定**——响应信封统一吗、分页结构对吗、没带 token 会不会被拦、**拿别人的题目 id 能不能改**。
- **服务集成形态**：从 Service 进去。问的是**协作**——submit 之后事务有没有回滚、会话表 / 作答表 / 作答统计表三处的状态一致吗。

怎么选：**验约定与边界走 HTTP，验数据流转直接调 Service。** 硬把两者混在一起会写出两不像的测试。

## 端到端：为什么值得为它单独建一个工程

现有 CI 有一个**从头到尾都没填上的洞**：`mvn test` 不拉 Spring、镜像 job 只 `docker build`、而且 `ci.yml` 末尾明写「刻意不 `docker compose up`」。也就是说，**后端从来没有在流水线里被真正启动过**。

端到端填的就是这个洞。它做一件别层做不到的事：**端到端**地跑一遍「注册 → 建题 → 组卷 → 答题 → 判分 → 错题本」。

| 只有端到端能抓到的 | 为什么别层抓不到 |
|--------------------|------------------|
| 后端返回了、前端没渲染（例如判分反馈不显示） | 接口测试只看到「响应是对的」，看不到页面 |
| 路由跳错、提交后停在了别的题 | 不是接口行为，是界面状态 |
| 两端（PC / 移动）行为不一致 | 要真渲染出来才比得出来 |
| **排版里的几何事实**（横向溢出、越出可视区、文字被裁切） | 是纯数值断言，但要**真渲染出来**才量得到元素的矩形框 |

⚠️ 但要先把话说死：**端到端验证的是「显式断言到的那几条路」。** 它证明不了「没测的地方是对的」，排版也只覆盖下面「几何事实」那一类。详见下面两张表。

## 能保证什么 / 不能保证什么

写下来是为了**防止对它产生不切实际的期待**——尤其是「有了测试就等于都对了」这种期待。

| 维度 | 能做到 | 做不到 |
|------|--------|--------|
| 业务主链路 | ✅ 抽样验证（清单内那几条） | ❌ 穷尽组合（题型 × 状态 × 来源 × 网络 × 端，列出来上千条） |
| 关键业务规则的界面表现 | ✅ 只限**写进断言的那几条** | ❌ 没写进断言的一律不管 |
| 单个类的逻辑 | ✅ 单元层枚举 | ❌ 需要库才能验的逻辑（那属接口/集成层） |
| HTTP 契约与数据边界 | ✅ 接口层专门覆盖 | ❌ 界面是否呈现（属端到端） |
| UI 交互细节（悬停、禁用态、二次确认、键盘操作） | ❌ 除非法专门写 | — |
| **排版的几何事实**（溢出、越界、裁切） | ✅ 端到端层的几何断言覆盖 | ❌ 只覆盖断言到的那几个页面与视口 |
| **排版的审美与层级**（间距、重心、主次、对比） | ❌ 断言表达不了；AI 探索可粗筛、人眼把关 | ❌ **零自动化保证** |
| 前端组件内部状态（store、watch 触发次数） | ❌ 黑盒看不到 | 除非将来补组件测试 |
| 偶发 / 时序问题（竞态、泄漏、长时间退化） | ❌ 单次跑复现不了 | — |
| 线上运维（容器、nginx、证书、备份恢复） | ❌ 在测试视野外 | 归 `docs/operations/runbook.md` |
| 「线上这台机器扛不扛得住」 | ❌ CI 环境 ≠ 2C2G 的服务器 | 由部署与排障流程兜 |

**一句话**：它是「业务主链路的真实端到端保险」，**不是「全面质量保证」**。

## 排版怎么测：三类分工

⚠️ 这里最容易混的一点：**「不做视觉回归」不等于「排版不做测试」**。排版里有一半是**纯数值事实**，不需要基准截图也能断言。

| 类型 | 例子 | 谁来做 |
|------|------|--------|
| **几何事实** | 横向溢出跑出屏幕、元素越出可视区、文字被容器裁掉、出现横向滚动条 | **端到端层的几何断言**（进 CI） |
| **审美与层级** | 间距是否协调、视觉重心、主次是否分明、颜色对比 | **AI 探索顺手粗筛 + 人眼**（不进 CI） |
| **逐像素比对** | 同一页面与一张基准图比差异 | **不做**（见「明确不做」） |

**几何断言能进 CI 的原因**：浏览器能直接给出每个元素的「矩形框」（位置与宽高），于是「右边界有没有超出页面宽度」这类问题变成**数值比较**——**不需要基准图、也不需要 AI 判断**，因此可重复。

⚠️ 边界写在明处：

- **只做低假阳性的检查**（溢出 / 越界 / 裁切）。**不做「元素重叠」检测**——下拉菜单、浮层、tooltip 本来就该重叠，做它会大量误报，而误报会让人养成「红了也照合」的习惯；
- **视口只挑几个代表宽度**（建议 1280 / 768 / 375），不做全矩阵；
- 它**只覆盖断言到的页面**——没写到的页面，排版仍然只有人眼。

理由见 [ADR 0020 Amendment 1](../adr/0020-layered-test-system.md)。

## 明确不做

这些是**已定的边界**，不是在排期的待办——写在这里是为了不再回头纠结。

| 不做 | 理由 |
|------|------|
| **视觉回归截图比对** | ① 逐像素差异不影响业务正确性，且这类现象开发时打开页面**当场可见**，不像判分反馈那类静默错误；② 单人开发没有第二双眼睛审「新基线对不对」，等于自己给自己签字；③ 基线是入库的二进制、会持续膨胀，而 CI 上没装中文字体，中文界面的截图会渲染成方块，基线永远对不齐。⚠️ **它不等于「排版不做测试」**——几何事实由端到端层的断言覆盖，见上节 |
| **跨浏览器矩阵**（Firefox / WebKit） | 用户量小，Chromium 一个引擎够用，多引擎是纯成本 |
| **把端到端设成本机必跑** | 本机连不上 Docker Hub（[ADR 0010](../adr/0010-china-mirrors-for-build-deps.md)），且本机缓存会**掩盖**「干净环境才暴露」的坑（[ADR 0009](../adr/0009-glibc-build-image-and-dockerignore.md)）——本机跑它，得到的是弱保证加一份额外维护 |
| **把 AI 探索测试接进 CI 门禁** | 它不可重复、不产出断言（见下节），进不了确定性门禁 |
| **录制出来的 codegen 代码直接进库** | 录制录的是人的全部行为（脆弱文案定位器、死等、无关动作），产物必须人工重写才能用 |

## 前端组件测试与 lint：暂缓，不是明确不做

两个前端工程（PC 与移动端）**没有单测、没有 lint**。这一条分两层看：

- **「前端工程不引额外依赖」是刻意的形态**——保持「随手能跑」的个人项目手感，不是为了省事而漏掉。所以端到端被**隔离在一个独立工程**里（`e2e/` 带自己的 `package.json`），前端工程的依赖树一个字不动。
- **组件测试（Vitest 之类）与 lint 本轮暂缓**——理由是无共享组件库、Element Plus 与 wot-design-uni 已兜底大部分交互，投入产出比不足。它是**暂缓**（记在 `docs/todo/2026-10-04-TODO-测试系统落地.md`），**不是明确不做**：将来若出现「多个页面复用同一段自研逻辑」，就该回来重新评估。

## 跑在什么环境上

端到端与第二层跑在 **CI 的一次性环境**里，跑完整个 job 环境随 runner 销毁。

**「一次性环境」指**：在 CI job 内部临时拉起一整套「MySQL + 后端 + 前端 + 测试执行器」，`mysql:8` 用**空库**、Flyway 从零迁移，跑完什么都不留。

**不连本机 dev 库的三条理由**：

1. **不污染数据**——测试会灌注册账号、建题目、产生作答记录，连 dev 库的话这些全留在库里；
2. **不受本机状态影响**——本机库里可能有任意历史数据、容器状态不确定，CI 上每次从零才**可复现**；
3. **能暴露本机永远发现不了的坑**——「干净 Linux 上从零起来」这本身就是要验的一件事。

> **例外**：AI 探索测试**不用**这套环境，它手动触发、接本机 dev 库、用专用测试账号——见 [agent-exploration.md](./agent-exploration.md)。两者目标不同：这里是「可复现的回归」，那里是「一次性撞意外」。

**不建 `.env` 文件**：测试专用配置（JWT 密钥、库连接）**直接注入 job 的 env**。理由是 `.env` 一旦入库就成了**第二份会漂的配置真相源**（[ADR 0006](../adr/0006-bare-array-import-contract.md)）；这也正解开了 `ci.yml` 里「不敢 `compose up`」那个结——那道坎的根因就是「仓库没有 `.env`，而密钥变量是必填断言」。

> 顺带一提：这类环境在项目里已有一个**半套先例**——`release.yml` 的迁移重放 job 就在一次性 `mysql:8` 上按序跑完 `db/migration`。区别是它**不起后端**，只验迁移语法。

## 加新功能时如何同步

同步**不靠记性**，靠一张表、一条规则、一条机械守卫。

### 1. 改动 → 补哪层

| 改了什么 | 补哪层 | 具体补什么 |
|----------|--------|------------|
| 新增 / 改接口（Controller、DTO、VO） | 接口 | 响应信封、分页、错误码、鉴权、**数据边界**（拿别人的 id 来读写必须失败） |
| 判分 / 抽题 / 错题本 / 会话流转的规则 | 单元 **+** 服务集成 | 纯逻辑用单元；落库后的多表状态用服务集成 |
| 数据库结构（Flyway 迁移） | 服务集成 | 真库上跑通迁移；语法层另由 `release.yml` 覆盖 |
| 前端页面 / 路由 / 交互 | 端到端 | 补一条 spec，跑通用户能看见的那条路 |
| 只改样式 / 文案 / 排版 | **不补** | 不写新断言；但若这个页面已被几何断言覆盖，改动会自动被它检查到 |
| 类型定义 | **不补** | 已有 `typecheck` 与 `types` 镜像守卫 |
| CI / 脚本 / 部署 | **不补** | 属运维，走 `docs/operations/runbook.md` |

### 2. 同一个 PR

对应测试必须进**同一个 PR**，不许「先合功能、测试下轮补」。上下文一散，补测试就永远不会发生——而「以后补」在本项目里本来就是禁止的表述。

### 3. 机械守卫兜底

一条 CI 检查：**每个 `module/*/controller` 至少有一个对应的测试类**。它把「新模块配了测试」从约定变成可验证事实，照 `ci.yml` 里 `types` 镜像 `diff` 守卫的先例。

⚠️ 两个已知局限，写在明处：
- 它**只验「有测试类」，验不了「断言有没有到点子上」**——防遗忘的兜底，不是质量保证；
- 它**要等接口层铺满现有 6 个模块才能打开**，否则一上线就是红的。

### 4. 什么不用补

反向清单同样重要，否则每个改动都会背上「必须写测试」的包袱：**只改样式 / 文案 / 排版不用补**（不写新断言；已被几何断言覆盖的页面会自动检到）、**只改类型不用补**（`typecheck` 与镜像守卫已覆盖）、**只改 CI 与部署脚本不用补**（那是运维流程）。

### 5. 什么时候要动这套系统本身

**加一层、加一个端（如小程序）、加一个新运行环境**，都属于系统变更——**必须走一条新 ADR**，不许在功能 PR 里顺手加。理由见 [ADR 0021](../adr/0021-test-sync-discipline.md)。

### 6. 加测试**不需要改文档**

文档从不列测试清单与数量（数量会变，清单必然漂）。所以「同步」这件事的负担被压到了最低：**写了测试就跑，文档一个字都不动**。这是刻意的设计，不是疏忽。

## 探索测试：不是测试

除了上面三层，还有一种由 AI 驱动的**探索测试**：给定任务与红线，让 AI 像真实用户一样自己决定点什么，撞出没人写过的路径。

它**不叫测试**，区别是本质的：

| | 脚本测试（三层） | 探索测试 |
|---|---|---|
| 路径 | 预先写死 | 现场自主决定 |
| 结果 | 断言通过 / 失败 | **一份报告**（现象 + 期望 vs 实际 + 复现步骤） |
| 可重复 | 是 | **否**（同一操作两次跑不一样） |
| 能当门禁 | 是 | **否**（今天绿明天红，会逼人关掉它） |
| 抓到的 bug | 补一条 spec 就**永久钉住** | 下次不一定还能撞到 → **必须回写成 spec 才留得住** |
| 能补哪块空白 | — | **排版里的审美与层级**（几何断言表达不了的那半），以及没人想到要写脚本的路 |

它的正确位置是：**三层之后的一层补充**，手动触发。任务书见 [agent-exploration.md](./agent-exploration.md)。

两条与它有关的约定：

- **报告不进仓库**。它写到一个**不进 git 的本地目录**，因为报告描述的是「探的那天系统怎么表现」，代码一改就陈旧——仓库里留一份会过期的副本正是 [ADR 0006](../adr/0006-bare-array-import-contract.md) 的失效模式。真正值得留的东西**永远有落点**：能固化的写成 spec，没定论的进 [todo](../todo/)。
- **任务书必须自包含、平台无关**。执行它的 AI 可能来自任何平台，因此它**不依赖任何平台的项目规则自动加载**（那些机制只在部分工具里生效），而是把该读的文档显式列出来；能力不足时**要求它在报告里声明缺了什么**，而不是默默跳过。

## 本文件用到的几个词

| 词 | 定义 | 不要叫 |
|----|------|--------|
| 单元测试 | 隔离测单个类，不拉 Spring、不碰库 | — |
| 接口测试 | 走 HTTP 验约定与边界 | 不要叫「集成测试」（太含糊） |
| 服务集成测试 | 真 Spring + 真库，直接调 Service 验事务与多表流转 | 不要叫「集成测试」 |
| 端到端测试 | 从浏览器界面走完整业务链路 | 不要叫「UI 测试」（界面只是它的入口） |
| 探索测试 | AI 自主决定路径、产出报告而非断言 | **不要叫「测试」** |

**这五个词不进 `CONTEXT.md`**——那里只收「本上下文独有的概念」（「知识点」被取消就是这个门槛），而这五个是通用技术词。定名仍要做，但落在本文件。
